# تدقيق عزل بيانات المحطات — Shelf API

- المستودع: `abdallah1mohmmed2/Water-provision`
- الفرع: `feature/firebase-station-foundation`
- النطاق: مراجعة `server/lib/server.dart`
- الحالة: **تدقيق أولي — توجد ثغرات تمنع تشغيل عدة محطات على قاعدة مشتركة**
- قاعدة العمل: لا تعديل أو دمج إلى `main` دون موافقة صريحة.

## 1. الخلاصة

نجاح Flutter Analyze والاختبارات وSonarCloud وبناء APK لا يعني أن عزل المحطات مكتمل. مراجعة المسارات أظهرت استعلامات وعمليات كتابة لا تقيد السجلات بمحطة المستخدم. لا يجوز نشر API متعدد المحطات أو استخدام قاعدة مشتركة قبل معالجة البنود الحرجة وإضافة اختبارات عزل فعلية.

هذا المستند يسجل ما ظهر في الكود؛ لا يدّعي أن الثغرات عولجت.

## 2. نتائج مؤكدة من الكود

| الخطورة | الموضع | الملاحظة |
|---|---|---|
| حرجة | `_dashboard` | إحصاءات المستفيدين والطابور والحجوزات والجلسات والإيرادات والمدفوعات والمصروفات تحسب من جميع المحطات. |
| عالية | `_settings` و`_settingsPut` | قراءة الإعدادات وتعديلها تتم على جدول عام دون نطاق محطة. |
| عالية | `_beneficiaryStatement` | يسترجع سقايات المستفيد بالمعرّف فقط ولا يتحقق من ملكية المستفيد للمحطة أولاً. |
| حرجة | `_irrigations` | قائمة السقايات لا تحتوي شرط `i.station_id = ?`. |
| حرجة | `_irrigationCancel` | يلغي السقاية بشرط المعرّف فقط، دون التحقق من محطة السجل. |
| عالية | `_sessions` | قائمة الجلسات لا تقيد المضخة/المستفيد بمحطة المستخدم. |
| حرجة | `_sessionFinishUnsafe` و`_sessionPostpone` | جلب/تعديل الجلسة يعتمد على المعرّف فقط؛ يلزم ربطها بمضخة المحطة والتحقق قبل التعديل. |
| عالية | `_sessionStart` | يتحقق من المضخة والمستفيد، لكنه لا يتحقق من ملكية `queue_id` و`booking_id` إن أرسلهما العميل. |
| عالية | `_queue` و`_queueAdd` | قراءة الطابور وترتيب المواضع عامان؛ الإضافة لا تتحقق صراحة من أن المستفيد يتبع المحطة. |
| حرجة | `_queuePostpone` و`_queueSkip` | تعديل صف الطابور بالمعرّف فقط دون تحقق من محطة المستفيد. |
| عالية | `_bookings` | قائمة الحجوزات لا تقيدها بمحطة المستفيد. |
| حرجة | `_bookingSchedule` و`_bookingCancel` | تعديل الحجز بالمعرّف فقط. |
| حرجة | `_payments` | قائمة المدفوعات لا تقيد الطرف/الصندوق بمحطة المستخدم. |
| عالية | `_cashboxTransferUnsafe` | يجب التحقق من ملكية الصندوقين قبل قراءة الأرصدة أو تعديلها، لا بعد تنفيذ التعديلات. |
| حرجة | `_diesel` ومخزون الديزل | القراءة وحساب المخزون يجمعان حركات جميع المحطات. |
| حرجة | `_expenses` و`_expenseCreateUnsafe` | قائمة المصروفات غير مقيدة؛ إنشاء المصروف لا يتحقق بشكل كافٍ من ملكية الصندوق وطريقة الدفع قبل تعديل الرصيد. |
| حرجة | `_journalReport` و`_ledger` | التقارير المحاسبية لا تقيد القيود بمحطة المستخدم. |
| حرجة | `_reports` و`_reportRows` | استعلامات التقارير لا تستقبل `stationId` وتقرأ جداول عامة أو السقايات دون نطاق محطة. |
| حرجة | `_backup` و`_restore` | النسخ والاستعادة يتعاملان مع ملف SQLite الكامل؛ في قاعدة مشتركة قد يكشف النسخ بيانات محطات أخرى أو يستبدلها. |

## 3. لماذا لا نضيف شروطاً عشوائية؟

بعض الجداول التشغيلية لا يظهر من مسارات الإنشاء الحالية أنها تحتوي `station_id` مباشرة، مثل الجلسات والطابور والحجوزات والمدفوعات والمصروفات وحركات الديزل والقيود. يجب تحديد علاقة الملكية المعتمدة لكل جدول عبر المضخة أو المستفيد أو العامل أو الشريك أو الصندوق أو المستخدم المنشئ، وفحص مخطط SQLite الفعلي والترحيلات قبل كتابة SQL جديد.

إضافة شرط `station_id` إلى جدول لا يحتوي هذا العمود ستكسر الخادم. وربط جدول عبر علاقة اختيارية بطريقة خاطئة قد يخفي سجلات صحيحة أو يسمح بتجاوز العزل.

## 4. خطة المعالجة المطلوبة

1. جرد مخطط SQLite الفعلي لكل جدول وفهارسه ومفاتيحه الأجنبية، وتحديد مالك المحطة لكل سجل.
2. اعتماد نطاق موحد في الخادم يستخرج `stationId` من JWT فقط، مع helpers آمنة للقراءة والتحديث والحذف.
3. إصلاح جميع مسارات القراءة والتجميع والتقارير لتطبيق نطاق المحطة، بما فيها الاستعلامات الفرعية وعمليات UNION.
4. إصلاح عمليات الكتابة بحيث تتحقق من ملكية كل مرجع أجنبي قبل أي تعديل، مع تنفيذ العملية كلها داخل معاملة واحدة.
5. إضافة `station_id` أو علاقة ملكية صريحة للجداول التي لا تملك نطاقاً موثوقاً؛ مع migration متوافق لا يغير أو يحذف بيانات المحطات الحالية.
6. فصل إعدادات كل محطة، وحسابات دفتر الأستاذ، ومخزون الديزل، والنسخ الاحتياطية حسب سياسة ملكية موثقة.
7. منع النسخ والاستعادة على ملف مشترك حتى تتوفر آلية نسخة خاصة بالمحطة مع تحقق صارم من هوية المحطة ومخطط النسخة.
8. إضافة اختبارات تكامل بمحطتين على قاعدة واحدة: إنشاء سجلات متشابهة، ثم إثبات أن المحطة A لا تقرأ أو تعدل أو تلغي أي سجل للمحطة B، والعكس.
9. إضافة اختبارات للتقارير والإحصاءات والمخزون والقيود والتحويلات والنسخ الاحتياطي، وليس فقط اختبارات middleware.
10. تشغيل Dart tests وFlutter Analyze وFlutter tests وSonarCloud وبناء APK بعد كل مجموعة إصلاحات.

## 5. بوابة القبول

لا يُعلن اكتمال عزل المحطات إلا إذا نجحت اختبارات المحطتين على قاعدة بيانات واحدة، وأثبتت أن جميع المسارات المحمية تقرأ وتكتب داخل نطاق المحطة، مع توثيق الترحيلات. إلى ذلك الحين:

- لا تفعّل مزامنة العمليات المالية.
- لا تنشر Shelf على الإنترنت.
- لا تعتبر نجاح CI الحالي دليلاً على جاهزية تعدد المحطات.
- لا تدمج هذا الفرع إلى `main` ضمن هذه المرحلة.
