# تدقيق عزل بيانات المحطات — Shelf API

- المستودع: `abdallah1mohmmed2/Water-provision`
- الفرع: `feature/firebase-station-foundation`
- النطاق: مراجعة `server/lib/server.dart`
- الحالة: **تدقيق أولي — توجد ثغرات تمنع تشغيل عدة محطات على قاعدة مشتركة**
- قاعدة العمل: لا تعديل أو دمج إلى `main` دون موافقة صريحة.

## 1. الخلاصة

نجاح Flutter Analyze والاختبارات وSonarCloud وبناء APK لا يعني أن عزل المحطات مكتمل. مراجعة المسارات أظهرت استعلامات وعمليات كتابة لا تقيد السجلات بمحطة المستخدم. لا يجوز نشر API متعدد المحطات أو استخدام قاعدة مشتركة قبل معالجة البنود الحرجة وإضافة اختبارات عزل فعلية.

هذا المستند يسجل ما ظهر في الكود؛ لا يدّعي أن الثغرات عولجت.

## 3. لماذا لا نضيف شروطاً عشوائية؟

بعض الجداول التشغيلية لا يظهر من مسارات الإنشاء الحالية أنها تحتوي `station_id` مباشرة، مثل الجلسات والطابور والحجوزات والمدفوعات والمصروفات وحركات الديزل والقيود. يجب تحديد علاقة الملكية المعتمدة لكل جدول عبر المضخة أو المستفيد أو العامل أو الشريك أو الصندوق أو المستخدم المنشئ، وفحص مخطط SQLite الفعلي والترحيلات قبل كتابة SQL جديد.

إضافة شرط `station_id` إلى جدول لا يحتوي هذا العمود ستكسر الخادم. وربط جدول عبر علاقة اختيارية بطريقة خاطئة قد يخفي سجلات صحيحة أو يسمح بتجاوز العزل.

## 4. خطة المعالجة المطلوبة

1. جرد مخطط SQLite الفعلي لكل جدول وفهارسه ومفاتيحه الأجنبية، وتحديد مالك المحطة لكل سجل.
2. اعتماد نطاق موحد في الخادم يستخرج `stationId` من JWT فقط، مع helpers آمنة للقراءة والتحديث والحذف.
3. إصلاح جميع مسارات القراءة والتجميع والتقارير لتطبيق نطاق المحطة، بما فيها الاستعلامات الفرعية وعمليات UNION.
4. إصلاح عمليات الكتابة بحيث تتحقق من ملكية كل مرجع أجنبي قبل أي تعديل، مع تنفيذ العملية كلها داخل معاملة واحدة.
5. إضافة `station_id` أو علاقة ملكية صريحة للجداول التي لا تملك نطاقاً موثوقاً؛ مع migration متوافق لا يغير أو يحذف بيانات المحطات الحالية.
6. فصل إعدادات كل محطة، وحسابات دفتر الأستاذ، ومخزون الديزل، والنسخ الاحتياطية حسب سياسة ملكية موثقة.
7. منع النسخ والاستعادة على ملف مشترك حتى تتوفر آلية نسخة خاصة بالمحطة مع تحقق صارم من هوية المحطة ومخطط النسخة.
8. إضافة اختبارات تكامل بمحطتين على قاعدة واحدة: إنشاء سجلات متشابهة، ثم إثبات أن المحطة A لا تقرأ أو تعدل أو تلغي أي سجل للمحطة B، والعكس.
9. إضافة اختبارات للتقارير والإحصاءات والمخزون والقيود والتحويلات والنسخ الاحتياطي، وليس فقط اختبارات middleware.
10. تشغيل Dart tests وFlutter Analyze وFlutter tests وSonarCloud وبناء APK بعد كل مجموعة إصلاحات.

## 5. بوابة القبول

لا يُعلن اكتمال عزل المحطات إلا إذا نجحت اختبارات المحطتين على قاعدة بيانات واحدة، وأثبتت أن جميع المسارات المحمية تقرأ وتكتب داخل نطاق المحطة، مع توثيق الترحيلات. إلى ذلك الحين:

- لا تفعّل مزامنة العمليات المالية.
- لا تنشر Shelf على الإنترنت.
- لا تعتبر نجاح CI الحالي دليلاً على جاهزية تعدد المحطات.
- لا تدمج هذا الفرع إلى `main` ضمن هذه المرحلة.

- حركة الديزل تتحقق من ملكية السقاية المرتبطة.

1. `settings` ما زال جدولاً عاماً بمفاتيح غير مرتبطة بمحطة؛ يجب تصميم ترحيل station-scoped مع سياسة واضحة لإعدادات المحطة الحالية قبل تعدد المحطات.
2. `backup` و`restore` ما زالا يتعاملان مع ملف SQLite كاملاً؛ يجب تعطيلهما في بيئة متعددة المحطات أو تصميم نسخة محطة مستقلة ومتحقق منها.
3. مخزون الديزل القديم الذي لا يحمل `created_by` ولا يرتبط بسقاية لا يمكن نسبه بأمان إلى محطة؛ يلزم ترحيل/مطابقة تاريخية قبل اعتماد رصيد المخزون.
4. تقارير القيود والمدفوعات والمصروفات التي تعتمد `created_by` تحتاج مراجعة بيانات تاريخية المستخدمين المنقولين بين المحطات؛ الأفضل إضافة `station_id` موثوق إلى السجلات المالية بترحيل يحفظ التاريخ.
5. يلزم اختبار عزل شامل للوحة التحكم والمدفوعات والمصروفات والديزل والتحويلات والقيود والتقارير والنسخ الاحتياطية، وليس فقط المسارات التي يغطيها الاختبار الحالي.
6. يلزم تدقيق جميع مسارات إنشاء/تعديل/حذف العامل والشريك والمدفوعات والمصروفات والديزل وربط كل المراجع الأجنبية بالمحطة داخل معاملة واحدة.
7. إعدادات المستفيد ورموز الدخول تحتاج rate limiting وسياسة واضحة لتكرار أرقام الهواتف عبر المحطات؛ مسار طلب الرمز يبحث برقم الهاتف دون station context.
8. لا توجد بعد ترحيلات مخطط واختبارات بيانات حقيقية من قاعدة محطة الإنتاج؛ اختبارات SQLite المصغرة تثبت فقط السلوك للمسارات التي تغطيها.
9. لا تزال المزامنة المالية ممنوعة حتى يكتمل Outbox/Inbox وidempotency واختبارات التكرار والتعارض.

## 8. إيقاف النسخ والاستعادة الكاملة مؤقتاً — 7 نوفمبر 2026

أُوقف مسارا `POST /api/v1/backup` و`POST /api/v1/restore` مؤقتاً وأصبحا يرجعان HTTP 409 برسالة واضحة. السبب أن `VACUUM INTO` يصدر ملف SQLite كاملاً، وأن الاستعادة تستبدل ملف قاعدة البيانات التشغيلي كاملاً؛ وهذا يتجاوز نطاق محطة JWT وقد يكشف أو يستبدل بيانات محطات أخرى.

هذا إجراء احترازي مقصود وليس تنفيذ نظام نسخ احتياطي بديل. لا تُعد ميزة النسخ/الاستعادة متاحة عبر API حتى تصميم تصدير واستيراد خاص بالمحطة، مع التحقق من station_id ومخطط الملف وسلامة العلاقات والقيود داخل عملية ذرية واختبارات استعادة فعلية.


## 9. تثبيت ملكية قيود الأستاذ عند الإنشاء — 7 نوفمبر 2026

كشف فحص مسارات المحاسبة أن `journal_entries` يحتوي `station_id` بالفعل، لكن دالة إنشاء القيود `_journal` لم تكن تكتب هذه القيمة. كما كانت بعض تقارير القيود والدفتر تعتمد على المحطة الحالية للمستخدم المنشئ بدلاً من ملكية القيد المحفوظة؛ وهذا قد يغيّر نطاق السجل التاريخي إذا نُقل المستخدم لاحقاً بين المحطات.

عولج ذلك في الفرع الحالي كما يلي:

- اشتقاق `station_id` من سجل المستخدم النشط داخل قاعدة البيانات، وليس من قيمة يرسلها العميل.
- رفض إنشاء القيد إذا لم يوجد مستخدم نشط أو محطة صالحة.
- حفظ `station_id` صراحة مع كل قيد جديد.
- جعل تقارير اليومية والدفتر وتقارير القيود تعتمد على `journal_entries.station_id`.
- إضافة اختبار تكامل يثبت أن قيداً ينشأ من جلسة مستخدم المحطة 7 يحمل `station_id=7`.

**حدود المعالجة:** القيود القديمة التي بقي `station_id` فيها فارغاً لم تُنسب إلى محطة بالتخمين، ولم تُعدّل. كما أن هذه المعالجة لا تغلق بعد إسناد ملكية المدفوعات والمصروفات وحركات الديزل التاريخية؛ يلزم تدقيق سجلاتها وربطها بمراجعها الموثوقة وتصنيف السجلات اليتيمة قبل أي ترحيل.
