# تصميم قاعدة البيانات المركزية وترحيل الخادم إلى PostgreSQL

- المستودع: `abdallah1mohmmed2/Water-provision`
- فرع العمل: `feature/firebase-station-foundation`
- الحالة: قرار تصميم وخطة تنفيذ مرحلية؛ **لم يتم إنشاء قاعدة PostgreSQL أو استضافة الخادم بعد**.
- لا دمج إلى `main` دون موافقة صريحة.

## القرار المستهدف

اعتماد المعمارية التالية:

1. **SQLite محلية** داخل كل تطبيق/جهاز للعمل دون اتصال.
2. **Shelf API + JWT** كواجهة الخادم الحالية، مع استمرار التحقق من المستخدم والمحطة والدور على كل طلب.
3. **PostgreSQL مركزية** بوصفها قاعدة البيانات الخادمية الدائمة، وتحتوي نسخة الأعمال المركزية الفعلية لكل محطة، لا سجل الأحداث وحده.
4. **Outbox/Inbox وسجل أحداث** للمزامنة، ومنع التكرار، وترتيب الأحداث، واكتشاف التعارضات والتدقيق.
5. **نسخ احتياطية مستقلة** لقاعدة PostgreSQL، مع اختبار استعادة دوري. سجل الأحداث وحده ليس نسخة احتياطية كاملة.

لا يُعتمد Firestore كقاعدة بيانات أعمال أو وسيط مزامنة في هذا القرار.

## الوضع الفعلي الذي تم التحقق منه في الكود

- `server/pubspec.yaml` يعتمد `sqlite3`، و`server/lib/server.dart` يستورد `package:sqlite3/sqlite3.dart` ويستقبل `Database` مباشرة.
- منطق الخادم يستخدم واجهات SQLite-specific مثل `db.select`, `db.execute`, `lastInsertRowId`, `BEGIN IMMEDIATE`, `PRAGMA`, و`sqlite_master`.
- الخادم يملك بالفعل مسارات أعمال وجداول محلية خاصة به، إضافة إلى جداول `sync_event_log` و`sync_entity_versions`.
- مسار `POST /api/v1/sync/events` يسجل الحدث والإصدار ويكشف التعارض؛ **لا يطبق payload الوارد كصف عمل داخل جداول الأعمال الخادمية**. ومسار Inbox يعيد الأحداث المقبولة للأجهزة الأخرى.
- لذلك لا يجوز وصف الوضع الحالي بأنه نسخة PostgreSQL مركزية كاملة من SQLite الموجودة على الهواتف. كما لا يجوز اعتبار سجل الأحداث وحده نسخة احتياطية كاملة لبيانات المحطة.

## لماذا لا نبدل SQLite بـ PostgreSQL بتغيير dependency فقط؟

الخادم مرتبط مباشرة بسلوك SQLite في الاستعلامات والمعاملات والمفاتيح التلقائية وفحص المخطط. استبدال حزمة قاعدة البيانات وحدها سيكسر أجزاء من الخادم أو يغير دلالات العمليات المالية. يجب أولاً عزل الوصول إلى البيانات وتوحيد المعاملات، ثم ترحيل SQL والمخطط واختبار كل مسارات الأعمال.

## مراحل التنفيذ الإلزامية

### المرحلة 0 — جرد وتثبيت العقد
- جرد نقطة تشغيل الخادم، ومكان إنشاء/فتح ملف SQLite، وكل الجداول والفهارس والقيود والمشغلات.
- توثيق جميع استعلامات SQLite-specific ومناطق المعاملات، خصوصاً العمليات المالية وInbox/Outbox.
- تحديد سياسة النسخ الاحتياطي والاستعادة، والاحتفاظ، وتشفير النقل والتخزين.
- لا تُنقل بيانات حقيقية قبل أخذ نسخة قابلة للاستعادة وتوثيق بصمتها.

### المرحلة 1 — طبقة وصول قابلة للتبديل
- إنشاء واجهة/طبقة repository أو database adapter واضحة بدلاً من تمرير `sqlite3.Database` إلى منطق HTTP مباشرة.
- توحيد المعاملات، وإرجاع المعرفات المنشأة، والصفوف، وأخطاء القيود.
- الإبقاء على SQLite كـ adapter اختباري مؤقت حتى تثبت الاختبارات عدم تغير السلوك.

### المرحلة 2 — مخطط PostgreSQL
- إنشاء migrations إصدارية للمخطط المركزي؛ لا تعتمد على إنشاء الجداول وقت تشغيل HTTP.
- تحويل الأنواع والمفاتيح الأجنبية والفهارس وقيود CHECK وUNIQUE إلى PostgreSQL.
- جعل كل جداول الأعمال وسجلات المزامنة والتدقيق مرتبطة بـ `station_id`، مع قيود/سياسات تمنع عبور بيانات المحطات.
- استخدام معاملات PostgreSQL الحقيقية للعمليات المحاسبية المركبة.
- استخدام استعلامات `RETURNING id` بدلاً من `lastInsertRowId`، وبدائل صريحة لاستعلامات SQLite الخاصة.

### المرحلة 3 — نقل عمليات الخادم
- نقل تسجيل الدخول، الجلسات، إدارة المحطة، الأطراف، السقايات، الطابور، الدفعات، المصروفات، الديزل، الصناديق، القيود والتقارير تدريجياً.
- نقل Sync event log وentity versions إلى PostgreSQL مع الحفاظ على idempotency ومؤشرات Inbox وعزل المحطات.
- لا يتم قبول حدث مزامنة كصف أعمال مركزي إلا بعد التحقق من UUID العالمي والعلاقات والإصدار وقواعد المجال، داخل معاملة واحدة.
- لا تُنفذ كتابة مزدوجة غير منضبطة بين SQLite وPostgreSQL. يُستخدم ترحيل مضبوط مع مقارنة أعداد الصفوف والمجاميع المالية.

### المرحلة 4 — الاختبارات والتحقق
- تشغيل اختبارات الخادم على PostgreSQL حقيقية في CI (خدمة PostgreSQL معزولة)، لا الاكتفاء بـ SQLite in-memory.
- اختبار عزل محطتين، تكرار الأحداث، إعادة استخدام event_id، ترتيب Inbox، العلاقات، التعارضات، وإعادة المحاولة بعد الانقطاع.
- اختبارات مالية للتحقق من توازن القيود وثبات مجموع الأرصدة قبل النقل وبعده.
- اختبار ضغط واتصالات متزامنة، ثم اختبار ترقية/رجوع مخطط موثق.
- لا تعتبر مرحلة الترحيل ناجحة قبل نجاح `dart analyze` و`dart test` واختبارات Flutter وAPK حسب نطاق التغيير، وظهور نتائج GitHub Actions النهائية للـ commit نفسه.

### المرحلة 5 — النشر والاستعادة
- نشر Shelf API على خادم HTTPS، وربطه بقاعدة PostgreSQL مُدارة أو خادم قاعدة بيانات خاص.
- حفظ `DATABASE_URL` وJWT secrets في إعدادات أسرار مزود الاستضافة فقط؛ لا توضع في Git أو التطبيق أو ملفات docs.
- تفعيل TLS، صلاحيات قاعدة بيانات بأقل امتياز، قيود الشبكة، ومراقبة صحة الخدمة.
- نسخ احتياطية آلية مشفرة، ونسخ خارج مزود قاعدة البيانات، وسياسة احتفاظ، واختبار استعادة إلى بيئة منفصلة.
- لا تُفعّل مزامنة مالية إنتاجية قبل نجاح استعادة تجريبية وموافقة مالك المحطة على خطة التحويل.

## ما يتطلب تدخلاً خارج التطبيق

لا يستطيع تطبيق Android إنشاء حساب استضافة أو قاعدة بيانات إنتاجية آمنة من تلقاء نفسه. يلزم مالك المشروع أن ينشئ/يعتمد حساب الاستضافة، ويحدد المنطقة وخطة التكلفة ووسيلة الدفع، ثم يضيف أسرار الاتصال إلى إعدادات النشر. بعد ذلك يمكن أتمتة migrations والنشر والفحوصات من GitHub Actions دون تضمين الأسرار في المستودع.

## بوابة الأمان الحالية

حتى تكتمل المراحل أعلاه:
- يبقى الخادم الحالي على SQLite كما هو.
- لا نغير عنوان الخادم الإنتاجي ولا إعدادات الأجهزة.
- لا نعلن أن PostgreSQL أو النسخ السحابية قد أُنشئت.
- لا نزيل SQLite المحلية أو Outbox/Inbox.
- لا ندمج التغييرات إلى `main`.


## نتائج الجرد الأولي للكود — 8 نوفمبر 2026

- نقطة تشغيل Shelf API هي `server/bin_server.dart`، وتفتح قاعدة البيانات عبر `sqlite3.open(config.databasePath)`.
- إعداد `SAQIA_DB` في `server/lib/server_config.dart` افتراضه الحالي `../saqia_station_v2.db`؛ ويمكن تغييره بمتغير بيئة. هذا مسار ملف SQLite وليس خدمة قاعدة بيانات سحابية.
- عنوان الربط الافتراضي `127.0.0.1`، والمنفذ الافتراضي `8080`، وسر JWT مطلوب من البيئة.
- كائن `SaqiaServer` في `server/lib/server.dart` يستقبل `sqlite3.Database` مباشرة، ويحتوي عمليات SQL SQLite-specific وعمليات أعمال كثيرة. لذلك نقل قاعدة الخادم يتطلب تعديل نقطة التشغيل وطبقة الوصول ومنطق الاستعلامات، وليس إعداد `DATABASE_URL` فقط.
- لا يوجد في الملفات التي تم فحصها إعداد PostgreSQL أو Docker deployment أو اتصال مُدار بقاعدة سحابية. لا يعني وجود مجلد `server` أو إعداد Firebase أن الخدمة منشورة.

هذا الجرد يثبت أول بوابة: **قاعدة الخادم الحالية ملف SQLite محلي يحدده SAQIA_DB**. الخطوة البرمجية التالية قبل إضافة اتصال PostgreSQL هي جرد كامل للمخطط والاستعلامات وعقود المعاملات، ثم فصل الوصول للبيانات واختبار ذلك دون تغيير نتائج العمليات الحالية.


## تقدم الخطوة التالية — جرد المخطط (8 نوفمبر 2026)

تم إنشاء `docs/POSTGRES_SCHEMA_INVENTORY.md` بعد فحص `assets/db/001_initial.sql` و`lib/data/local/database.dart` و`server/lib/server.dart`. يؤكد الجرد أن مخطط تطبيق المحطة عند الإصدار 28، وأن الخادم يعتمد على وجود جداول الأعمال ولا ينشئ المخطط الكامل بنفسه؛ فهو ينشئ جداول المصادقة المحدودة وسجل المزامنة فقط ويجري ترقيات ملكية المحطة عند توفر الجداول.

**بوابة التنفيذ التالية:** تثبيت schema مرجعي نهائي من SQLite v28 (بما فيه ترقيات 2–28 والجداول المساعدة وTriggers) ومقارنته بقاعدة فعلية منزوعة البيانات الحساسة، ثم كتابة PostgreSQL migrations. لم يبدأ إنشاء PostgreSQL DDL للأعمال بعد، تجنباً لإنتاج مخطط ناقص من ملف التأسيس وحده.
