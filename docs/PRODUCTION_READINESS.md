# جاهزية API ساقية كمصدر مالي مركزي

## الحالة الحالية

الخادم الحالي ليس جاهزًا ليكون مصدرًا ماليًا مركزيًا. ما زالت واجهة Flutter تحفظ العمليات المالية في SQLite المحلية. بوابة Firebase الحالية تدير المصادقة وطلبات الوصول والمحطات، لكنها لا ترحّل القيود أو المدفوعات. وخادم Shelf الموجود مستقل عن Flutter وFirebase، ويستخدم JWT خاصًا واستعلامات SQLite مباشرة. كشف التدقيق فروقًا في التسعير والإلغاء والديزل، وقصورًا في عزل المحطات ومنع تكرار الطلبات، إضافة إلى مسارات مالية لا تنفذ المعنى المحاسبي نفسه الذي ينفذه التطبيق. لذلك لا ينبغي توجيه أي كتابة مالية إنتاجية إليه الآن.

أُضيف أساس Worker في `server/worker-api/`: تحقق من Firebase ID token، وقراءة عضوية UID والمحطة عبر Firestore REST، مع رفض عمليات المال افتراضيًا. اجتازت النسخة الحالية 15 اختبارًا محليًا، وتحليل Node، وفحص اعتمادات (`npm audit` بلا ثغرات عالية)، وتجميع Wrangler باستخدام `--dry-run`. لم تُجرَ اتصالات إلى مشروع Firebase الفعلي، ولم تُنشأ أسرار أو يُنشر Worker؛ لذلك هذه الاختبارات لا تثبت اتصال الإنتاج أو التكافؤ المالي. جميع مسارات `/api/v1/finance/*` ترجع `503` عمدًا.

## الاتجاه التقني المختار للتجهيز

يبقى Firebase Spark دون ربط فوترة. مسارات Cloud Functions وCloud Run داخل Firebase لا تدخل في هذا التصميم لأن الوصول إليها يتطلب Blaze. توفّر Spark حصص Firestore المجانية، لكن عند تجاوز حصة منتج ذي حصة يومية يُوقف استخدام ذلك المنتج حتى دورة الفوترة التالية؛ وتعرض صفحة Firebase الحالية حدود Firestore المجانية، ومنها 50 ألف قراءة و20 ألف كتابة يوميًا و1 GiB تخزين.[1]

خيار الاستضافة المجاني المرشح هو **Cloudflare Workers Free** كطبقة API خارج Firebase، مع Firestore قاعدة البيانات المركزية الدائمة. تذكر وثائق Cloudflare حدًا مجانيًا قدره 100 ألف طلب يوميًا و10 ms من وقت CPU لكل استدعاء؛ كما تُظهر تجاوز حد الطلبات بخطأ 1027.[2] [3] يجب اختبار التحقق من الرموز وتوقيع طلبات Google REST ضمن حد CPU الفعلي، وضبط الأخطاء بحيث ترفض العملية بأمان ولا تتجاوز API عند بلوغ الحصة. لا يُستخدم `SAQIA_DB` أو SQLite كقاعدة تشغيل لهذا Worker.

استُبعد Render Free كمضيف لمصدر مالي إنتاجي؛ فوثائقه تنص على أن الخدمات المجانية ليست للإنتاج، وتدخل في السكون بعد 15 دقيقة من عدم النشاط، كما أن نظام الملفات مؤقت وقد تُفقد الملفات المحلية عند السكون أو إعادة التشغيل.[8]

## المصادقة والتفويض المقترحان

يرسل تطبيق Flutter Firebase ID token إلى الـAPI عبر HTTPS. يتحقق الخادم من توقيع الرمز ومشروع Firebase و`aud` و`iss` ووقت الصلاحية، ثم يستخرج UID. يمكن استخدام Firebase Admin SDK أو مكتبة JWT مع مفاتيح Firebase العامة والتحقق من المطالبات المطلوبة.[5]

بعد ذلك يعيد الخادم قراءة العضوية النشطة والدور والمحطة ونطاق الحساب من Firestore عند كل عملية مالية حساسة. لا يثق بـ`role` أو `stationId` مرسلين من التطبيق. وإذا استُخدم حساب خدمة للوصول إلى Firestore من API، تُحفظ مفاتيحه في Cloudflare Secrets ولا تدخل Git أو Flutter.[4] [9] يجب منح حساب الخدمة أقل دور IAM يفي بحاجة القراءة والكتابة.

مهم: استدعاءات Firestore الموثقة بحساب خدمة تستخدم IAM وتتجاوز Firestore Security Rules؛ لذلك يجب أن يفرض الـAPI بنفسه كل فحوص الهوية والمحطة والدور وحالة الحساب. قواعد Firestore الحالية تظل مغلقة أمام الكتابة المالية المباشرة من العميل.[6] [7]

## بوابات إلزامية قبل اعتماد المصدر المركزي

1. توحيد مخطط السجل المالي وتحديد العملة ودقة الأعداد الصحيحة، ومراجع القيود، وهوية المنفذ، وحالات المسودة والاعتماد والترحيل والعكس.
2. نقل التحقق من الهوية والعضوية والدور والمحطة إلى الخادم لكل طلب. يجب إزالة الرجوع الصامت إلى المحطة `1` وتقييد كل قراءة وكتابة وتقرير بالمحطة التي حلّها الخادم.
3. توحيد قواعد المدفوعات والمصروفات والتحويلات والري والديزل والشمسي والقيود والإلغاء مع التطبيق المحلي. لا تكفي مطابقة أسماء المسارات.
4. تنفيذ كل عملية مالية كمعاملة ذرية، مع `idempotency key` فريد يمنع تكرار العملية بعد انقطاع الشبكة أو إعادة المحاولة، وحفظ الأصل مع قيد عكسي موثق بدل تعديل السجلات المرحلة.
5. إنشاء اختبارات مقارنة بين SQLite الحالية والـAPI الجديد تشمل جميع الأدوار والمحطات، الفشل والتزامن وإعادة المحاولة والإلغاء وتوازن الأستاذ. لا يُعتمد التبديل إلا بعد تطابق مجاميع الحسابات والسجلات.
6. اختبار النسخ والاستعادة ونقل بيانات اصطناعية أو نسخة منقحة أولًا، مع مطابقة عدد السجلات والأرصدة والقيود المرجعية والتحقق من إمكانية الرجوع.

## تسلسل التنفيذ الآمن

يبدأ التجهيز بخدمة API منفصلة قابلة للاختبار محليًا، وFirestore Emulator، وبيانات تركيبية فقط. بعد ذلك تُنفذ وحدات الأعمال وتُقاس حدود Cloudflare وFirestore. تبقى قاعدة SQLite المحلية كما هي، وتُحفظ نسخة احتياطية قبل أي تجربة بيانات حقيقية. لا يحدث قطع إلى المصدر الجديد ولا حذف لقاعدة محلية ضمن مراحل التطوير. نشر النسخة النهائية يحتاج بعد اجتياز جميع البوابات، ولا يعني نشر الكود وحده اعتمادها ماليًا.
