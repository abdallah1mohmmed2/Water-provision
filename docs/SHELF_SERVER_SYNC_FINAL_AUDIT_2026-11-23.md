# التدقيق النهائي للخادم Shelf وخطة استكمال المزامنة

- المستودع: `abdallah1mohmmed2/Water-provision`
- الفرع الذي تمت مراجعته: `feature/unified-theme-system`
- رأس الفرع وقت التدقيق: `90119b9af27599f0d65ba20a49ff714e306c43f3`
- تاريخ التدقيق: 2026-11-23
- نوع العمل: مراجعة توثيقية/ساكنة للكود وسجلات CI؛ لا تمثل اعتماد نشر إنتاجي.
- لم تُعدّل هذه المراجعة أي منطق مالي أو قاعدة بيانات أو إعداد تشغيل.

## 1. الخلاصة التنفيذية

Shelf ليس حزمة تجريبية أضيفت إلى المشروع فقط. يوجد خادم HTTP فعلي مبني بـ `shelf` و`shelf_router`، ويقدم REST API تحت `/api/v1`. كما توجد آلية Offline-First تشمل SQLite محلية، وOutbox، وSyncService، وInbox، ومعالجات أحداث أعمال داخل الخادم.

الغرض من الخادم هو أن يكون جهة تحقق واعتماد مركزية لعمليات المحطة عند الاتصال، مع إبقاء العمل المحلي متاحاً عند انقطاع الشبكة. لا ينبغي أن يثق الخادم في الرصيد أو القيد المحاسبي المرسل من الهاتف؛ بل يتحقق من أمر العمل ويعيد إنشاء آثاره المالية داخل معاملة ذرية، ثم يرسل الإسقاطات المعتمدة للأجهزة الأخرى.

**الحالة ليست اكتمالاً إنتاجياً:** توجد مجالات مزامنة متبقية، وتطبيقات العامل والشريك لم يثبت اكتمال ربطها بالمصادقة والمزامنة، كما أن قاعدة الخادم الحالية SQLite وليست PostgreSQL، ولم يثبت نشر الخادم أو اختبار محطة إنتاج وهاتفين فعليين.

## 2. لماذا بُني Shelf؟

وفق `docs/ARCHITECTURE_DECISION_SHELF_OFFLINE_FIRST.md`، القرار هو اعتماد Shelf API + JWT كواجهة خلفية موحدة للتطبيقات الأربعة: الإدارة، المستفيد، العامل، الشريك.

الأهداف:
1. توحيد التحقق من الهوية والمحطة والدور على الخادم، وعدم الاعتماد على صلاحيات يقررها العميل.
2. جعل الخادم جهة اعتماد أوامر الأعمال والآثار المحاسبية المركزية عند الاتصال.
3. استمرار العمل دون اتصال عبر SQLite محلية وقائمة Outbox، ثم استلام التغييرات عبر Inbox عند عودة الشبكة.
4. منع تكرار السقاية والقبض والمصروف والقيود التابعة عند إعادة إرسال الطلب.
5. فصل أوامر الأعمال الأصلية عن الآثار المشتقة: القيد، سطور القيد، استحقاق العامل/الشريك، حركة الديزل، وتحديث رصيد الصندوق.
6. تمهيد الانتقال إلى PostgreSQL عند الحاجة إلى استضافة مركزية أو تعدد محطات أكبر، دون نقل غير مدروس أو فقد بيانات.

Firebase ليس قاعدة البيانات المحاسبية في هذا القرار. إعداد Firebase Authentication الموجود يخص بوابة إتاحة Android، ولا يحل محل JWT أو Shelf ولا يمثل Firestore مزامنة مالية.

## 3. ما تأكد وجوده في الكود

### 3.1 الخادم والمصادقة
- نقطة التشغيل: `server/bin_server.dart`.
- التطبيق: `server/lib/server.dart`.
- الإعدادات: `server/lib/server_config.dart`.
- الحزم: `shelf` و`shelf_router` و`sqlite3` وJWT وArgon2id.
- إعداد التشغيل يرفض سر JWT الافتراضي أو القصير، ويستخدم `127.0.0.1` افتراضياً، مع منفذ افتراضي 8080 ومسار قاعدة من `SAQIA_DB`.
- تسجيل الدخول الإداري يتحقق من الحساب النشط والدور والمحطة، وتوجد حماية لمحاولات الدخول.
- كلمات مرور الحسابات تُرحّل تدريجياً إلى Argon2id عند نجاح الدخول القديم.

### 3.2 مسارات المزامنة
يوجد في Router:
- `POST /api/v1/sync/events`
- `GET /api/v1/sync/inbox`

خدمة العميل `lib/services/sync_service.dart` تنشئ أحداثاً بمعرف UUID ثابت، وهوية سجل عالمية، ونسخة أساسية، ومعرف جهاز. كما تثبت الحمولة قبل الإرسال حتى لا تتغير عند إعادة المحاولة.

الخادم يتحقق من UUID ونوع الكيان والعملية وحجم الحمولة، ويقارن إعادة استخدام `event_id` بالمصدر والحمولة والعملية والنسخة. ويستخدم سجل أحداث وإصدارات ومؤشرات تسلسلية، ويطبق معالجات مجال داخل حدود معاملات/Savepoints.

Inbox المحلي يحفظ الأحداث قبل تحريك المؤشر، ويطبقها عبر `SyncInboxApplier.apply` داخل معاملة مع `captureSync: false` لمنع إعادة الحدث الوارد إلى Outbox. ويهيئ `SyncCoordinator` الخدمة باستخدام `SyncService.withInboxHandler`، ثم ينفذ Push/Pull/Apply عند الاتصال وعودة التطبيق، مع إعادة محاولة دورية.

### 3.3 ملكية الآثار المالية
يوجد مبدأ واضح في الكود والتوثيق: يرسل العميل أمر العمل الأصلي، ولا يرسل القيود أو الأرصدة المشتقة كأوامر مستقلة عندما ينشئها الخادم. يجب الحفاظ على هذا المبدأ لكل مجال، بما فيه السقايات والمدفوعات والمصروفات والتحويلات والديزل واستحقاقات الأطراف.

### 3.4 قاعدة البيانات والنشر
- الخادم يفتح SQLite عبر `sqlite3.open` ومسار `SAQIA_DB`.
- `storage_contract.dart` يحتوي عقداً/واجهة تمهيدية، لكنه لا يحتوي محول PostgreSQL أو MySQL فعلياً.
- الخادم يستخدم تفاصيل SQLite مباشرة مثل `select/execute` و`BEGIN IMMEDIATE` و`PRAGMA` و`lastInsertRowId`.
- لا يوجد دليل من الملفات التي راجعتها على نشر إنتاجي أو TLS/Reverse Proxy أو قاعدة PostgreSQL مُدارة أو إعداد استعادة إنتاجي.
- عنوان الربط الافتراضي محلي؛ لا يُفتح على الإنترنت مباشرة. يلزم HTTPS أمامه عند النشر.

## 4. حالة المزامنة حسب سجل الإنجاز

الحالات التالية من سجل `docs/SYNC_ACCOUNTING_READINESS_AND_WORK_LEDGER.md`، وهي نطاقات قبول تاريخية موثقة وليست شهادة على تشغيل أجهزة إنتاجية:

| المجال | الحالة المسجلة | قرار الاستكمال |
|---|---|---|
| P0 عقد الأحداث والآثار التابعة | مكتمل بالأدلة المسجلة | لا يعاد تنفيذه؛ تُصلح فقط فجوة جديدة مثبتة |
| P1 تعديل/إلغاء السقايات | مكتمل ضمن نطاقه | لا تعاد كتابة معالجاته |
| P2 القبض والصرف والاستبدال والإلغاء | مكتمل ضمن نطاقه | أعد استخدام مسار payments القائم ولا تنشئ مساراً مكرراً |
| P3a/P3b | منفذان ومختبران ضمن شرائحهما | يحافظ عليهما |
| P3c رواتب العامل الثابتة/الشهرية | تنفيذ موجود، لكن قبول CI غير مثبت في سجل الحالة | تحقق من أحدث SHA قبل الإغلاق أو إعادة العمل |
| P3d توزيع الأرباح الدوري | مقبول باختبارات CI ضمن النطاق الموثق | لا يعاد تنفيذه |
| P3e السلف/الإيداعات/التسويات/العكوس | غير مكتمل | جرد العمليات المحلية ثم تنفيذ الفجوات فقط |
| P3f كشوف الأطراف الخاصة والصلاحيات | غير مكتمل | تدقيق خصوصية العامل والشريك وصلاحيات كل دور |
| P4 فجوات الديزل | متبقٍ بحسب السجل | تدقيق الإلغاء والتصحيح فقط، لا إعادة إنشاء المسارات المقبولة |
| P5 الحسابات العامة | متبقٍ | مزامنة الحركات وإلغاؤها/عكسها |
| P6 التسويات والإقفالات والمطابقات | متبقٍ | عقد مالي ذري ومقارنة نتائج الطرفين |
| P7 إعدادات المحطة والكيانات المساندة | متبقٍ | عزل كل محطة ومصدر إعداداتها |
| P8 التكامل الشامل | متبقٍ | اختبارات نهاية إلى نهاية وتعدد الأجهزة والمحطات |

لا تعتبر قائمة `_syncEntityTypes` دليلاً على وجود handler. يجب التحقق لكل نوع من وجود معالج صريح، وOutbox صحيح، وملكية محطة، وصلاحيات، وآثار ذرية، وسياسة replay/conflict، واختبارات قبول.

## 5. التعارضات والتقادم في الوثائق

### 5.1 وثيقة القرار المعماري
في مقدمة `docs/ARCHITECTURE_DECISION_SHELF_OFFLINE_FIRST.md` يوجد تنبيه يقر بأن بعض وصف المزامنة قديم، لكن القسم 6 ما زال يذكر أن مسارات المزامنة غير موجودة، وأن SyncService يرسل لمسار قديم، وأن UUID/Idempotency غير مكتمل، وأن كلمات المرور SHA-256. هذه العبارات لا تطابق التنفيذ الحالي الذي يحتوي مساري sync، ومعالجات أعمال، وUUID/Idempotency، وترحيل Argon2id.

### 5.2 خطة قاعدة البيانات المركزية
`docs/CENTRAL_DATABASE_MIGRATION_PLAN.md` يذكر أن الخادم يسجل الحدث فقط ولا يطبق الحمولة على جداول الأعمال. هذا الوصف تاريخي ولا يطابق `_applySyncBusinessEvent` الحالي الذي يوجه أحداثاً إلى معالجات أعمال خادمية وينشئ آثاراً مالية. يجب تحديث الوثيقة مع إبقاء حقيقة أن PostgreSQL لم تُنفذ بعد.

### 5.3 بروتوكول المزامنة وخطة إكمال Firebase
بعض أقسام `docs/SYNC_PROTOCOL_AND_INBOX.md` و`docs/FIREBASE_STATION_COMPLETION_PLAN.md` تصف الخادم كسجل أحداث فقط، وتذكر أن تطبيق أحداث الأعمال المركزية لم يبدأ. هذه الأقسام يجب فصلها بوضوح إلى «خط أساس تاريخي» و«الحالة الحالية»، لأن سجل P0 اللاحق يثبت تنفيذ إسقاطات ومعالجات خادمية أوسع.

### 5.4 حالة المشروع ومصفوفة التتبع
- `docs_STATUS.md` ما زال يحتوي عبارات قديمة مثل أن منطق الخادم منفصل/غير مشمول، ولا يعكس مراحل P0–P3d المسجلة لاحقاً.
- `docs_REQUIREMENTS_TRACEABILITY.md` مصفوفة ربط متطلبات بمسارات ملفات؛ وجود المسار لا يثبت اختبار التشغيل أو اكتمال API.
- يوجد فرق بين تقارير Flutter المحلية وتقارير Shelf API: تدقيق التقارير في `STATION_ISOLATION_SECURITY_AUDIT.md` يذكر أن API يدعم خمسة تقارير فقط، وأن التقارير الأخرى ترجع 501 عمداً إلى أن تنفذ باختبارات عزل. لا ينبغي الخلط بين 24 تقريراً في واجهة التطبيق و24 تقريراً خادمياً مكتملاً.

### 5.5 اختلاف الفرع المرجعي
وثائق القرار والسجل تشير إلى `feature/firebase-station-foundation`، بينما تمت هذه المراجعة على `feature/unified-theme-system`. الفرع الذي تمت مراجعته يتقدم على فرع Firebase foundation بـ47 التزاماً وفق مقارنة GitHub، لكن بيانات الفرع المستهدف داخل بعض الوثائق لم تُحدّث. يجب اعتماد اسم فرع واحد في سجل الحالة قبل أي دفعة لاحقة.

## 7. خطة الاستكمال المقترحة — دون إعادة العمل

### المرحلة 0 — تثبيت الحقيقة والتوثيق
1. اعتماد `feature/unified-theme-system` كفرع العمل الحالي أو تحديد فرع آخر صراحة.
2. تحديث وثيقة القرار المعماري: إزالة العبارات التاريخية المتعارضة أو وسمها بوضوح، وتوثيق المسارات والعقود الحالية.
3. تحديث `docs_STATUS.md` ومصفوفة التتبع لتفصل بين «موجود بالكود»، «مختبر محلياً»، «مقبول في CI»، و«مختبر على أجهزة فعلية».
4. توحيد رأس سجل الإنجاز مع الفرع وSHA الحاليين.

### المرحلة 1 — P3e: سلف وإيداعات وتسويات وعكوس العامل والشريك
1. جرد كل أنواع `worker_transactions` و`partner_transactions` في `AccountingService` مع كل `type/reference_type`.
2. إعادة استخدام مسار P2 القائم لمدفوعات العامل والشريك؛ لا تضف Outbox root أو handler مكرراً.
3. فصل سلف العامل/الشريك النقدية عن سلفة ديزل المستفيد وعن المديونية الافتتاحية `opening_balance/previous_debt`.
4. لكل عملية ناقصة: أمر أعمال واحد، UUID عالمي، تحقق JWT والمحطة والدور، مبلغ/تاريخ/طرف معتمد من الخادم، قيد متوازن وأثر صندوق عند الحاجة، وإلغاء/عكس مرتبط بالأصل دون حذف.
5. اختبارات replay، حدث جديد لنفس الأصل، مرجع محطة أجنبية، صلاحية غير كافية، فشل منتصف المعاملة، عميلين مستقلين، وتطابق الأستاذ وكشف الطرف.

### المرحلة 2 — P3f: خصوصية كشوف العامل والشريك
1. تحديد ما الذي يراه العامل عن حسابه وما الذي يراه الشريك عن حسابه.
2. منع الشريك من الاطلاع على أرصدة أو حركات الشركاء الآخرين، مع تحديد ما إذا كانت رؤية عمليات المحطة العامة مسموحة وفق قرار المنتج.
3. إنشاء جلسات وأدوار خادمية مستقلة للعامل والشريك، وعدم إعادة استخدام صلاحيات الإدارة.
4. اختبار منع الوصول عبر تغيير المعرفات أو UUID، واختبار كشف الحساب والتقارير والتنزيلات.

### المرحلة 3 — P4: إغلاق فجوات الديزل
- مراجعة `docs/FIREBASE_DIESEL_SYNC_STATUS.md` ومسارات التصحيح/الإلغاء الحالية.
- عدم إعادة تنفيذ إنشاء حركات الديزل أو الاستهلاك الذي تثبته اختبارات سابقة.
- كل تصحيح أو إلغاء يجب أن يحفظ الأصل، ويضيف حركة عكسية مرتبطة، ويطابق المخزون والصندوق والقيد على الجهازين.

### المرحلة 4 — P5 وP6 وP7
- P5: الحسابات العامة وحركاتها، مع الرصيد المحسوب من سجل الحركات لا من قيمة يرسلها العميل.
- P6: تسويات المحاسب، إقفالات الفترات، المطابقات، وإعادة الفتح بسبب وقيود عكسية.
- P7: إعدادات المحطة والكيانات المرجعية، مع مصدر موحد وعزل كامل لكل محطة.

تنفذ كل مرحلة منفردة، ويحدث السجل بعد نجاحها قبل الانتقال.

### المرحلة 5 — P8: قبول التكامل الشامل
اختبار عملي على خادم Shelf حقيقي وقاعدتي SQLite مستقلتين على الأقل:
- إنشاء أمر من جهاز، إرساله، واستلام أثره في الجهاز الثاني.
- timeout بعد قبول الخادم ثم إعادة إرسال الحدث نفسه.
- انقطاع بعد Pull وقبل Apply ثم إعادة تشغيل التطبيق.
- أكثر من صفحة Inbox، وتعارض تعديلين متزامنين.
- عدم إعادة إرسال Inbox إلى Outbox.
- عدم مضاعفة القيود أو الصندوق أو المخزون.
- عزل محطتين على قاعدة خادم مشتركة، بما يشمل التقارير والنسخ الاحتياطي.
- اختبار استعادة نسخة قبل أي ترحيل إنتاجي.

## 8. خطة PostgreSQL والنشر

لا يُنصح بنقل قاعدة الخادم إلى PostgreSQL قبل تثبيت عقود جميع العمليات والمخطط المرجعي. الخطة الصحيحة:
1. استخراج مخطط SQLite فعلي كامل من نسخة منزوعة البيانات الحساسة، بما يشمل migrations وtriggers والفهارس والعلاقات.
2. إنشاء Adapter حقيقي خلف `SaqiaStorageContract` واختبار SQLite adapter أولاً دون تغيير النتائج.
3. إنشاء PostgreSQL migrations إصدارية، مع `station_id` وعلاقات وفهارس وقيود واضحة.
4. نقل معاملات الخادم تدريجياً واختبارها على PostgreSQL حقيقية في CI.
5. مقارنة أعداد السجلات ومجاميع الحسابات والقيود قبل/بعد الترحيل.
6. نشر Shelf خلف HTTPS/Reverse Proxy، مع الأسرار خارج Git، وصلاحيات قاعدة بيانات محدودة، ومراقبة ونسخ احتياطية مشفرة واختبار استعادة.

لا يُستبدل SQLite المحلي على الأجهزة، ولا تجرى كتابة مزدوجة غير منضبطة بين SQLite وPostgreSQL.

## 9. بوابات القبول النهائية

لا تعتبر أي مرحلة مكتملة إلا عند تحقق جميع ما ينطبق عليها:
- اختبارات Dart للخادم ناجحة على SHA نفسه.
- Flutter Analyze وFlutter Tests ناجحة.
- اختبارا العميلين و/أو المحطتين ناجحان بحسب النطاق.
- إثبات توازن القيود وتطابق حسابات الأطراف والصندوق والمخزون.
- إثبات replay/idempotency وعدم echo وعدم فقد الأحداث.
- GitHub Actions بحالة نهائية SUCCESS على SHA نفسه.
- بناء APK وظهور Artifact صالح عند كون التغيير يستلزم بناء التطبيق.
- تحديث سجل الإنجاز بالـ SHA والملفات والاختبارات وروابط CI وقيود النطاق.
- لا دمج إلى `main` ولا نشر إنتاجي دون موافقة صريحة.

## 10. القرار المقترح

اعتماد هذه الوثيقة كمرجع مراجعة موحد لخطة استكمال Shelf والمزامنة، مع إبقاء سجل الإنجاز التفصيلي مرجعاً لإثبات كل دفعة. يبدأ التنفيذ بعد تثبيت الفرع، وبالترتيب P3e ثم P3f ثم P4 ثم P5 ثم P6 ثم P7 ثم P8. بعد ذلك فقط تُستكمل طبقة PostgreSQL والنشر المركزي.

**ممنوع إعادة بناء Shelf أو Outbox/Inbox من الصفر. وممنوع اعتبار وجود route أو handler أو اختبار مكتوب دليلاً على اكتمال مجال غير مقبول في CI.**
