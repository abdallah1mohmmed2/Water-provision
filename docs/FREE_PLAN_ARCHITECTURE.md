# معمارية ساقية ضمن Firebase Spark المجانية

**التاريخ:** 24 أكتوبر 2026
**النطاق:** تنفيذ مقيد بخطة Spark بعد موافقة المستخدم على Doha وFirestore والبريد/كلمة المرور. لم تتم ترقية Blaze أو إضافة حساب فوترة.

## الحالة التي جرى فحصها

المشروع الحالي `water-provision` ما زال على Spark. أُنشئت قاعدة Firestore القياسية في `me-central1` (Doha)، ونُشرت قواعد مقفلة ومختبرة على Emulator. فُعّل Firebase Authentication للبريد وكلمة المرور فقط؛ Phone/SMS وEmail link غير مفعّلين. أُنشئ حساب Auth واحد للمدير الأعلى وربطت قواعد الإنتاج UID ثابتًا به، مع اشتراط توثيق البريد؛ لا تُخزن كلمة مروره في الشيفرة. أضيفت في Flutter بوابة منفصلة لتسجيل الدخول، والتحقق بالبريد، وطلبات الانضمام، وإنشاء المحطات وإسناد العضويات من المدير الأعلى. لا توجد محطات أو عضويات أو بيانات تشغيلية سحابية بعد. تبقى عمليات التطبيق الإدارية والمحاسبية على SQLite المحلية، كما أن خادم Dart المنفصل غير موصول بالتطبيق وتوجد اختلافات محاسبية وصلاحيات بينه وبين التطبيق.

## ما يمكن فعله ضمن Spark

يمكن استخدام Firestore القياسي ضمن حصة مجانية لكل مشروع: قاعدة افتراضية واحدة، 1 GiB تخزين، حتى 50,000 قراءة و20,000 كتابة و20,000 حذف يوميًا، و10 GiB نقل بيانات شهريًا. تجاوز حصة Spark المجانية يوقف استخدام المنتج المعني حتى دورة لاحقة أو ترقية الخطة، ولا يتحول تلقائيًا إلى فوترة استخدام [1] [2].

الدخول الحالي بالبريد وكلمة المرور فقط؛ لا يُستخدم SMS ولا رمز تحقق محلي. لأن Firebase Client SDK لا يستطيع إنشاء حساب Auth لشخص آخر أو تعيين كلمة مروره بأمان، يسمح التطبيق للمستخدم بإنشاء حسابه ببريده والتحقق منه ثم إرسال طلب وصول. التسجيل لا يمنح أي قراءة لمحطة؛ المدير الأعلى وحده يحدد الدور والمحطة في معاملة محمية بالقواعد. قد يستهلك التسجيل العام حصص Authentication ويستلزم مراقبة الطلبات؛ لا يضاف مفتاح Admin SDK أو حساب خدمة إلى التطبيق. إذا لم تتوفر هوية بريد حقيقية، لا يُستبدل ذلك بحساب أو رمز محلي وهمي. تُخزّن أدوار `manager`, `accountant`, `operations`, `beneficiary`, `partner`, و`worker` في عضويات لا يستطيع المستخدم إنشاءها أو تعديلها.

المدير الأعلى مثبت بواسطة UID واحد في `firestore.rules` وملف `lib/core/cloud_admin_config.dart`، ويتطلب البريد الموثق. لا يملك هذا الحساب صلاحية مالية خاصة تتجاوز الأدوار؛ يستطيع إنشاء محطات ومراجعة طلبات وإسناد عضويات فقط. أدوار المستفيد والشريك والعامل تتطلب `subjectId` موجودًا بالفعل في المجموعة المناسبة داخل المحطة؛ لن تنشئ الشاشة سجلاتهم التشغيلية أو المالية.

إنشاء قاعدة Firestore يتطلب اختيار موقع جغرافي لا يمكن تغييره بعد تهيئة القاعدة. اختير `me-central1` (Doha) بعد معرفة أن المستخدمين في اليمن وموافقة المستخدم على الموقع المقترح [3]. اختيار المنطقة لا يعني نقل بيانات التطبيق المحلي إليها.

## حدود ما يمكن تأمينه بلا خادم موثوق

قواعد Firestore قادرة على منع الوصول غير المصرح، وفرض عضوية المحطة، وقصر القراءة على السجل الشخصي، والتحقق من حقول وحالات انتقال بسيطة. لهذا أضفت قواعد افتراضية الرفض واختبارات محلية تغطي الأدوار الستة، العزل بين المحطات، ومنع المستخدم من ترقية دوره. يمكن السماح للمستفيد بإنشاء طلب موعد غير مالي محدود الحقول، والسماح للمدير/التشغيل بمراجعته ضمن انتقالات حالة محصورة. يتطلب التطبيق أن تكون مستندات `operationalProfiles` خالية من الرصيد والأجور والدفتر؛ قواعد العميل لا تستطيع حذف حقول سرية من المستند عند قراءته، لذلك يكتب هذه المستندات مستقبلًا خادم موثوق أو مسار إعداد مراقب.

لكن القواعد ليست خادم أعمال محاسبيًا. لا ينبغي السماح لأي تطبيق عميل، حتى تطبيق المدير، بإنشاء قيود مالية أو مدفوعات أو تسويات أو إغلاقات فترات أو تعديل أرصدة ودفتر أستاذ. فالعميل قابل للتعديل، والقواعد لا تنفذ منطق النظام المحاسبي الكامل ولا تضمن وحدها تكامل عدة مستندات على نمط معاملات الأعمال الحالية. أوقفت الكتابة المباشرة لهذه البيانات في القواعد المضافة. حتى وجود خادم خارجي لا يجعل نقل هذه العمليات آمنًا تلقائيًا: يلزم نقل قواعد الأعمال من Dart واختبار التكافؤ المالي، وعزل المحطات، والتراجع عن القيود، والتكرار الآمن، قبل تحويل مصدر الحقيقة.

إلى حين بناء واختبار ذلك الخادم، يجب أن تبقى SQLite المحلية هي مصدر الحقيقة الحالي. لا يوجد مزامنة موثوقة متعددة الأجهزة في التصميم الحالي، ولن أضيف مزامنة توحي بأنها آمنة أو موثوقة قبل تحديد تعارضات البيانات ومصدر الحقيقة وخطة النسخ الاحتياطي.

## خيار API خارجي مجاني جرى فحصه

للحالات التي تتطلب API موثوقًا، الخيار الأولي الأنسب هو Cloudflare Workers Free، لا Cloud Functions أو Cloud Run. يحدد العرض المجاني 100,000 طلب يوميًا، و10 ms من CPU لكل استدعاء، وذاكرة 128 MB، و50 طلبًا فرعيًا لكل استدعاء. وعند تجاوز الحصة اليومية يرجع الخطأ 1027؛ يمكن ضبط المسارات الحساسة لتفشل مغلقة بدل تمرير الطلب دون تطبيق عامل الحماية [4] [5]. السرّ المخزن في Worker يُحفظ كقيمة مشفرة وغير ظاهرة في لوحة التحكم بعد تعريفه، ما يسمح بإبقاء أسرار GCP خارج Flutter والمستودع [6].

هذا خيار يحتاج تجربة قبل اعتماده: التحقق من Firebase ID token ومعالجة منطق العمل قد يتجاوزان حد CPU البالغ 10 ms؛ وثائق Cloudflare نفسها تشير إلى أن المصادقة أو تحليل المدخلات قد يستهلك 10–20 ms في بعض الحالات. عمليات الشبكة بحد ذاتها لا تدخل في وقت CPU [5]. لذلك يجب قياس التحقق من التوكن والقراءة/الكتابة الفعلية على Worker تجريبي قبل توجيه تطبيقات الإنتاج إليه.

الخادم يجب أن يتحقق تشفيريًا من Firebase ID token، بما في ذلك توقيع RS256 والمُصدر والجمهور والانتهاء، ثم يتحقق من الدور والمحطة على الخادم. توصي وثائق Firebase باستخدام Admin SDK أو مكتبة JWT مدققة، وتحذر من اعتبار التوكن صحيحًا لمجرد وصوله من العميل [7]. إذا احتاج Worker صلاحية Firestore إدارية، تحفظ بيانات الاعتماد في Secret مشفر لدى المستضيف، ولا تضاف إلى Flutter أو GitHub. ويجب أن يطبق الخادم التحقق من الدور والمحطة بنفسه لأن حساب الخدمة يستطيع تجاوز Firestore Security Rules.

راجعت أيضًا Render Free: المستضيف يصرّح بأن الخدمات المجانية ليست للإنتاج؛ تتوقف بعد 15 دقيقة دون حركة، وقد يستغرق تشغيلها مجددًا نحو دقيقة، ونظام الملفات مؤقت، كما أن قاعدة Postgres المجانية تنتهي بعد 30 يومًا. لذلك لا أوصي به لخادم محاسبي تشغيلي [8]. تعرض Deno Deploy خطة Free بمليون طلب شهريًا و10 ساعات CPU نشطة و20 GiB نقل صادر؛ لكن يلزم فحص شروط الحساب المتاحة وقياس توافق مكتبات Firebase قبل اختياره [9].

**التوصية:** لا نفعّل خادمًا خارجيًا الآن. نبني ونختبر قواعد Firestore محليًا، ثم نقيس Worker تجريبيًا بلا بيانات حقيقية. إن لم يتسع حد 10 ms للمعالجة الموثوقة، لا ننتقل إلى خطة مدفوعة؛ نبقي العمليات الحساسة في التطبيق المحلي ونعلن بوضوح أن API المركزي غير متاح ضمن الاختيار المجاني الحالي.

## ما أُضيف للاختبار الآمن

أضيفت `firestore.rules` مغلقة افتراضيًا. تتيح قراءة المحطة للأعضاء الفاعلين وفق الدور، وتقيّد المستفيد والشريك والعامل بملفاتهم وكشوفهم، ولا تسمح للعميل بكتابة أي سجلات مالية. أضيفت قواعد المدير الأعلى وإنشاء المحطات وطلبات وصول البريد الموثّق، واختُبرت القواعد في Firebase Emulator باستخدام المشروع التجريبي `demo-saqia-rules-tests` لا الإنتاج. نُشرت النسخة الحالية من القواعد إلى قاعدة الإنتاج بعد تطابقها حرفيًا مع الملف واجتياز 12 اختبارًا؛ وهي لا تفتح Firestore للعامة. أضيفت الشاشة إلى التطبيق وبُني APK debug بنجاح للاختبار فقط؛ لا يوجد توقيع إصدار إنتاج أو تثبيت على هاتف المستخدم. لم يُنشر API أو تتم مزامنة بيانات SQLite.

## الحالة والخطوات التالية

1. **مكتمل:** تحديد أن المستخدمين في اليمن واختيار Doha (`me-central1`) بعد الموافقة؛ القاعدة القياسية أُنشئت ولا يمكن تغيير المنطقة.
2. **مكتمل:** تفعيل Email/Password وإنشاء حساب المدير الأعلى وتثبيت UID الخاص به في القواعد. يجب على المالك توثيق البريد وتغيير كلمة المرور الابتدائية قبل الاستخدام الاعتيادي.
3. **مكتمل في الشيفرة:** تسجيل/تحقق بالبريد وطلب انضمام؛ المدير الأعلى ينشئ المحطات ويحدد الدور والمحطة للمستخدم. لا ينشئ التطبيق هويات Auth للآخرين ولا يستخدم رموزًا محلية.
4. **مكتمل:** تشغيل 12 اختبار Emulator محليًا تشمل التحقق من البريد، الطلبات، إنشاء المحطات، عزل المحطات، صلاحيات الأدوار الستة، subjectId، ومنع الكتابة المالية؛ نُشرت النسخة المطابقة من القواعد إلى الإنتاج.
5. إذا أُريد API مركزي مجاني، تنفيذ تجربة منفصلة على Cloudflare Workers وقياس حد CPU والتحقق من Firebase ID tokens. لم يُنشأ حساب استضافة أو يُنشر Worker.
6. **معلّق ومقصود:** ربط الشاشات التشغيلية والمحاسبية بمصدر سحابي ونقل بيانات SQLite. لا تُنفذ عمليات مالية أو ترحيل حتى تتوفر واجهة خادم موثوق وتنجح اختبارات تكافؤ محاسبي.
