# خطة إكمال ربط Firebase وتعدد المحطات

الفرع المستهدف: `feature/firebase-station-foundation`
المستودع: `abdallah1mohmmed2/Water-provision`

> هذه الوثيقة تسجل تدقيق المصدر وخطة الإكمال. لا تعني أن أي مرحلة تشغيلية أو اختبار محطة فعلية قد اجتازت القبول.

## نتيجة التدقيق الأولي للمصدر

| المجال | الحالة التي ظهرت في المصدر | المطلوب قبل اعتمادها |
|---|---|---|
| تهيئة Firebase | `firebase_core` موجود وتهيئة Android اختيارية عبر متغيرات بناء مقيدة بمعرف مشروع المحطة | استكمال خدمات المصادقة/البيانات المطلوبة وقواعد الأمان واختبار إعدادات كل محطة |
| Outbox/Inbox | **منفذة جزئياً**: يوجد `POST /api/v1/sync/events` و`GET /api/v1/sync/inbox`، ومعرف حدث ثابت، وقيد `(station_id,event_id)`، وcursor ومعالج Inbox محلي واكتشاف تعارضات | إكمال اختبارات القبول على رأس الفرع الحالي، وإثبات تطبيق أحداث الأعمال على المصدر المركزي؛ سجل الأحداث الحالي لا يطبق payload على جداول أعمال الخادم |
| Shelf API | `server/lib/server.dart` يقرأ ويكتب قاعدة SQLite مستقلة؛ لا يوجد في هذا التدقيق إثبات أن Flutter يقرأ ويكتب عبر مصدر موحد | تحديد نمط التشغيل المعتمد: API مصدر مركزي مع SQLite محلية كـ cache/outbox، أو نمط محلي صريح؛ ومنع مسارين متنافسين للكتابة |
| التقارير | `_reports` يعرف 24 نوعًا، لكن `supported` يضم خمسة تقارير فقط، والباقي يرجع 501 | تنفيذ كل تقرير أو إزالته من الواجهة، مع اختبارات عزل لمحطتين لكل استعلام |
| النسخ والاستعادة | نقطتا API `/backup` و`/restore` ترجعان 409 عمدًا لأن نسخ ملف SQLite المشترك غير آمن | تصدير واستيراد منطقي على مستوى station_id، مع manifest وتحقق وسجل وrollback |
| البيانات التاريخية | توجد محاولات backfill لبعض الجداول المالية، لكن لا توجد نتيجة تدقيق شاملة للسجلات ذات station_id الفارغ أو غير المتطابق | تقرير جرد read-only، تصنيف مؤكد/ملتبس/غير منسوب، وعدم إسناد الملتبس تلقائيًا |
| الاستضافة | لا يوجد ضمن المصدر الذي تمت مراجعته إثبات إعداد نشر TLS/Secrets/health checks | نشر تجريبي آمن، TLS، أسرار خارج المستودع، نسخ احتياطية، مراقبة واختبار عزل محطتين |

## ترتيب التنفيذ الإلزامي

### المرحلة 1 — عقد المزامنة Outbox/Inbox
- إنشاء جدول Outbox محلي بمعرف حدث UUID ثابت لا يتغير عند إعادة المحاولة.
- حالات واضحة: pending, sending, acknowledged, conflict, failed.
- إرسال دفعات محدودة مع station identity من جلسة موثوقة، لا من payload يختاره العميل.
- Inbox خادمي بقيد UNIQUE على (station_id, event_id) لضمان exactly-once effect حتى مع at-least-once delivery.
- إقرار يتضمن event_id وserver_sequence ونتيجة التطبيق.
- Pull عبر cursor ثابت، مع Inbox محلي يمنع إعادة تطبيق الحدث.
- كشف تعارضات version/updated_at وتسجيلها دون الكتابة فوق بيانات مالية بصمت.
- اختبارات: إعادة الإرسال، انقطاع الاتصال، إعادة ترتيب الأحداث، duplicate event، حدث لمحطة أخرى، تعارض تعديلين، rollback عند فشل التطبيق.

### المرحلة 2 — مصدر بيانات موحد بين Flutter وShelf
- اعتماد Repository واحد في Flutter يوجه القراءة والكتابة عبر API عند تفعيل الخادم.
- SQLite المحلية مخزن offline cache وOutbox فقط في وضع الخادم؛ لا تنفذ نفس العملية محليًا وخادميًا مرتين.
- عقود DTO وvalidation مشتركة موثقة، وإصدارات API واضحة.
- إبقاء وضع Local-only الحالي صريحًا عندما لا يكون الخادم مهيأً.

### المرحلة 3 — التقارير واختبارات العزل
- إكمال التقارير الـ19 غير المدرجة في مجموعة التقارير المنفذة الحالية.
- تمرير station_id من claims فقط.
- إضافة fixtures لمحطتين ببيانات متداخلة المعرفات قدر الإمكان.
- لكل تقرير: اختبار أن نتائج المحطة A لا تتضمن أي صف من B والعكس، مع اختبارات الفلاتر والتواريخ والأدوار.

### المرحلة 4 — نسخ واستعادة محطة واحدة
- تنسيق تصدير منطقي يتضمن station manifest/schema version وتعداد الصفوف وبصمة SHA-256.
- تصدير الجداول المرتبطة بالمحطة وفق علاقاتها، دون بيانات المحطات الأخرى.
- التحقق من هوية المحطة والروابط والمجاميع قبل الاستعادة.
- الاستعادة داخل معاملة أو staging database ثم تبديل ذري مع rollback.
- رفض النسخة الموجهة لمحطة أخرى إلا عبر إجراء نقل صريح ومدقق.

### المرحلة 5 — البيانات التاريخية
- تشغيل تقرير تدقيق read-only لكل الجداول التي تحمل station_id أو ترتبط بها.
- تصنيف السجلات: منسوبة بثقة، قابلة للاستنتاج بعلاقة وحيدة، متعارضة، مجهولة.
- لا يُنفذ backfill إلا للحالات ذات علاقة وحيدة مثبتة؛ المتعارض/المجهول يبقى دون إسناد ويصدر تقرير مراجعة.
- حفظ عدد السجلات قبل وبعد كل ترحيل وسجل تدقيق.

### المرحلة 6 — الاستضافة واختبار محطتين
- إعداد متغيرات البيئة والأسرار خارج Git، TLS فقط، CORS محدود، rate limits، health/readiness endpoints.
- إعداد مراقبة وأخطاء ونسخ احتياطية دورية للخادم.
- اختبار قبول على قاعدتي محطة فعليتين بعد أخذ نسخ احتياطية وموافقة أصحاب البيانات.
- إثبات منع القراءة والكتابة والتقارير والنسخ عبر حدود المحطات.
- اختبار استعادة محطة دون التأثير على المحطة الثانية.

## بوابة القبول

لا تُعلن الجاهزية قبل إرفاق:
1. نتائج `dart format`, `dart analyze`, واختبارات Dart للخادم.
2. نتائج `flutter pub get`, `flutter analyze`, `flutter test` وبناء APK.
3. تقرير اختبارات API isolation لمحطتين.
4. تقرير مزامنة يثبت duplicate suppression وconflict handling.
5. تقرير تصدير/استعادة لمحطة واحدة مع إثبات بقاء المحطة الثانية دون تغيير.
6. تقرير السجلات التاريخية غير المنسوبة.
7. رابط الاستضافة ونتيجة TLS واختبار المحطتين.

## قيود السلامة

- لا دمج إلى `main` ضمن هذه المهمة.
- لا حذف أو إعادة كتابة بيانات تاريخية تلقائيًا.
- لا اعتبار إعداد Firebase client config سرًا؛ مفاتيح Admin/service account لا توضع في التطبيق أو المستودع.
- لا تشغيل restore على قاعدة فعلية قبل backup قابل للتحقق وخطة rollback.
- لا وصف أي بناء أو اختبار بأنه ناجح ما لم تنفذ الأداة فعليًا وتُظهر نجاحه.
