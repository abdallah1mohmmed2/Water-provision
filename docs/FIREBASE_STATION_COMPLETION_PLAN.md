المستودع: `abdallah1mohmmed2/Water-provision`

> هذه الوثيقة تسجل تدقيق المصدر وخطة الإكمال. لا تعني أن أي مرحلة تشغيلية أو اختبار محطة فعلية قد اجتازت القبول.

## نتيجة التدقيق الأولي للمصدر

| المجال | الحالة التي ظهرت في المصدر | المطلوب قبل اعتمادها |
|---|---|---|
| تهيئة Firebase | `firebase_core` موجود وتهيئة Android اختيارية عبر متغيرات بناء مقيدة بمعرف مشروع المحطة | استكمال خدمات المصادقة/البيانات المطلوبة وقواعد الأمان واختبار إعدادات كل محطة |
| Outbox/Inbox | **منفذة جزئياً**: يوجد `POST /api/v1/sync/events` و`GET /api/v1/sync/inbox`، ومعرف حدث ثابت، وقيد `(station_id,event_id)`، وcursor ومعالج Inbox محلي واكتشاف تعارضات | إكمال اختبارات القبول على رأس الفرع الحالي، وإثبات تطبيق أحداث الأعمال على المصدر المركزي؛ سجل الأحداث الحالي لا يطبق payload على جداول أعمال الخادم |
| Shelf API | `server/lib/server.dart` يقرأ ويكتب قاعدة SQLite مستقلة؛ لا يوجد في هذا التدقيق إثبات أن Flutter يقرأ ويكتب عبر مصدر موحد | تحديد نمط التشغيل المعتمد: API مصدر مركزي مع SQLite محلية كـ cache/outbox، أو نمط محلي صريح؛ ومنع مسارين متنافسين للكتابة |
| التقارير | `_reports` يعرف 24 نوعًا، لكن `supported` يضم خمسة تقارير فقط، والباقي يرجع 501 | تنفيذ كل تقرير أو إزالته من الواجهة، مع اختبارات عزل لمحطتين لكل استعلام |
| النسخ والاستعادة | نقطتا API `/backup` و`/restore` ترجعان 409 عمدًا لأن نسخ ملف SQLite المشترك غير آمن | تصدير واستيراد منطقي على مستوى station_id، مع manifest وتحقق وسجل وrollback |
| البيانات التاريخية | توجد محاولات backfill لبعض الجداول المالية، لكن لا توجد نتيجة تدقيق شاملة للسجلات ذات station_id الفارغ أو غير المتطابق | تقرير جرد read-only، تصنيف مؤكد/ملتبس/غير منسوب، وعدم إسناد الملتبس تلقائيًا |
| الاستضافة | لا يوجد ضمن المصدر الذي تمت مراجعته إثبات إعداد نشر TLS/Secrets/health checks | نشر تجريبي آمن، TLS، أسرار خارج المستودع، نسخ احتياطية، مراقبة واختبار عزل محطتين |

## ترتيب التنفيذ الإلزامي

### المرحلة 1 — عقد المزامنة Outbox/Inbox
- إنشاء جدول Outbox محلي بمعرف حدث UUID ثابت لا يتغير عند إعادة المحاولة.
- حالات واضحة: pending, sending, acknowledged, conflict, failed.
- إرسال دفعات محدودة مع station identity من جلسة موثوقة، لا من payload يختاره العميل.
- Inbox خادمي بقيد UNIQUE على (station_id, event_id) لضمان exactly-once effect حتى مع at-least-once delivery.
- إقرار يتضمن event_id وserver_sequence ونتيجة التطبيق.
- Pull عبر cursor ثابت، مع Inbox محلي يمنع إعادة تطبيق الحدث.
- كشف تعارضات version/updated_at وتسجيلها دون الكتابة فوق بيانات مالية بصمت.
- اختبارات: إعادة الإرسال، انقطاع الاتصال، إعادة ترتيب الأحداث، duplicate event، حدث لمحطة أخرى، تعارض تعديلين، rollback عند فشل التطبيق.

### المرحلة 2 — مصدر بيانات موحد بين Flutter وShelf
- اعتماد Repository واحد في Flutter يوجه القراءة والكتابة عبر API عند تفعيل الخادم.
- SQLite المحلية مخزن offline cache وOutbox فقط في وضع الخادم؛ لا تنفذ نفس العملية محليًا وخادميًا مرتين.
- عقود DTO وvalidation مشتركة موثقة، وإصدارات API واضحة.
- إبقاء وضع Local-only الحالي صريحًا عندما لا يكون الخادم مهيأً.

### المرحلة 3 — التقارير واختبارات العزل
- إكمال التقارير الـ19 غير المدرجة في مجموعة التقارير المنفذة الحالية.
- تمرير station_id من claims فقط.
- إضافة fixtures لمحطتين ببيانات متداخلة المعرفات قدر الإمكان.
- لكل تقرير: اختبار أن نتائج المحطة A لا تتضمن أي صف من B والعكس، مع اختبارات الفلاتر والتواريخ والأدوار.

### المرحلة 4 — نسخ واستعادة محطة واحدة
- تنسيق تصدير منطقي يتضمن station manifest/schema version وتعداد الصفوف وبصمة SHA-256.
- تصدير الجداول المرتبطة بالمحطة وفق علاقاتها، دون بيانات المحطات الأخرى.
- التحقق من هوية المحطة والروابط والمجاميع قبل الاستعادة.
- الاستعادة داخل معاملة أو staging database ثم تبديل ذري مع rollback.
- رفض النسخة الموجهة لمحطة أخرى إلا عبر إجراء نقل صريح ومدقق.

### المرحلة 5 — البيانات التاريخية
- تشغيل تقرير تدقيق read-only لكل الجداول التي تحمل station_id أو ترتبط بها.
- تصنيف السجلات: منسوبة بثقة، قابلة للاستنتاج بعلاقة وحيدة، متعارضة، مجهولة.
- لا يُنفذ backfill إلا للحالات ذات علاقة وحيدة مثبتة؛ المتعارض/المجهول يبقى دون إسناد ويصدر تقرير مراجعة.
- حفظ عدد السجلات قبل وبعد كل ترحيل وسجل تدقيق.

### المرحلة 6 — الاستضافة واختبار محطتين
- إعداد متغيرات البيئة والأسرار خارج Git، TLS فقط، CORS محدود، rate limits، health/readiness endpoints.
- إعداد مراقبة وأخطاء ونسخ احتياطية دورية للخادم.
- اختبار قبول على قاعدتي محطة فعليتين بعد أخذ نسخ احتياطية وموافقة أصحاب البيانات.
- إثبات منع القراءة والكتابة والتقارير والنسخ عبر حدود المحطات.
- اختبار استعادة محطة دون التأثير على المحطة الثانية.

## بوابة القبول

لا تُعلن الجاهزية قبل إرفاق:
1. نتائج `dart format`, `dart analyze`, واختبارات Dart للخادم.

6. تقرير السجلات التاريخية غير المنسوبة.

## قيود السلامة

- لا دمج إلى `main` ضمن هذه المهمة.
- لا حذف أو إعادة كتابة بيانات تاريخية تلقائيًا.
- لا اعتبار إعداد Firebase client config سرًا؛ مفاتيح Admin/service account لا توضع في التطبيق أو المستودع.
- لا تشغيل restore على قاعدة فعلية قبل backup قابل للتحقق وخطة rollback.
- لا وصف أي بناء أو اختبار بأنه ناجح ما لم تنفذ الأداة فعليًا وتُظهر نجاحه.

## تكليف التنفيذ التالي — توحيد البيانات وتطبيق المزامنة والتقارير

هذا التكليف يحدد ترتيب التنفيذ الملزم للطلبات الثلاثة، ولا يغيّر الحالة إلى مكتمل بمجرد وجود الوثائق أو مسارات API.

### A. توحيد مصدر البيانات بين Flutter وShelf

1. جرد جميع شاشات وعمليات الكتابة والقراءة التي ما زالت تصل مباشرة إلى SQLite عبر AppDatabase، وربط كل عملية بميزة/Repository.
2. إنشاء عقد API وDTOs لكل مجال قبل نقل الشاشة؛ لا تمرير SQL أو أسماء أعمدة حرة من Flutter.
3. اعتماد وضعين صريحين: Local-only حيث SQLite الحالية مصدر البيانات الوحيد، وServer-connected حيث Shelf هو المرجع المعتمد وSQLite المحلية cache وOutbox/Inbox فقط.
4. منع تنفيذ العملية نفسها محلياً وخادمياً مرتين؛ كل أمر يحمل UUID ثابتاً، وتكون نتيجة الخادم هي الإقرار النهائي.
5. الانتقال مجالاً بمجال: الإعدادات، المستفيدون، السقايات والجلسات، ثم المدفوعات والصناديق، ثم العاملون والشركاء والقيود. لا يتم تحويل كل الشاشات دفعة واحدة.
6. إضافة اختبارات Repository تثبت أن وضع Server-connected لا يستدعي كتابة SQLite المحلية كمرجع أعمال، وأن Local-only لا يتطلب الخادم.

### B. تطبيق أحداث المزامنة على جداول الأعمال

الحالة الحالية: /sync/events يسجل الحدث والإصدار في sync_event_log ويعيد accepted، لكنه لا يطبق الحمولة على جداول الأعمال. لذلك فإن accepted الحالي لا يعني أن قاعدة الأعمال المركزية تغيرت، ويجب عدم استخدامه كإقرار مزامنة مكتمل.

التنفيذ المطلوب:
1. تغيير دلالة الإقرار: لا يعاد accepted إلا بعد نجاح تطبيق الحدث على سجل الأعمال وتسجيل الحدث وتحديث الإصدار في المعاملة نفسها.
2. بناء معالج allow-list لكل مجال؛ يمنع SQL العام، ويمنع payload من تحديد station_id أو تجاوز صلاحيات المستخدم.
3. التحقق من هوية السجل العالمية والعلاقات الأجنبية، والتحقق من أن كل مرجع تابع للمحطة نفسها قبل أي كتابة.
4. create/update/delete يجب أن تكون عمليات نطاقية، مع منع تغيير هوية السجل أو نقله لمحطة أخرى.
5. عند فشل أي تحقق أو كتابة: rollback كامل، ولا يسجل الحدث كـ accepted ولا يتقدم إصدار الكيان.
6. إعادة إرسال الحدث نفسه تعيد نتيجة العملية السابقة دون أثر ثانٍ؛ وإعادة استخدام event_id بحمولة مختلفة ترفض.
7. لا يسمح بتطبيق العمليات المالية قبل توفير معالجاتها الخاصة التي تعيد احتساب القيود والأرصدة من قواعد العمل، ولا تقبل رصيداً محسوباً من العميل.
8. اختبارات لكل مجال: إنشاء/تعديل/حذف، تكرار الحدث، تعارض الإصدار، مرجع مفقود، مرجع من محطة أخرى، وفشل منتصف المعاملة مع إثبات rollback.

### C. التقارير وعزل المحطات

1. جرد كل اسم تقرير ظاهر في Flutter ومقارنته بالتنفيذ الفعلي في Shelf؛ لا يكفي وجود الاسم في allow-list.
2. تنفيذ التقرير أو إبقاؤه صراحةً 501 REPORT_NOT_IMPLEMENTED مع إزالة ادعاء توفره من الواجهة. يمنع إرجاع صفوف تقرير آخر كبديل.
3. تمرير station_id من JWT فقط إلى كل استعلام رئيسي وفرعي وUNION وتجميع، وعدم قبول station_id من query أو body.
4. تثبيت ملكية السجلات المالية التاريخية في أعمدة صريحة أو علاقات ملكية موثوقة؛ لا تعتمد التقارير على محطة المستخدم الحالية إذا كان ذلك يغير ملكية سجل تاريخي.
5. بناء fixtures لمحطتين على قاعدة واحدة، تتضمن سجلات متشابهة ومعرفات متداخلة حيث يسمح المخطط، ثم اختبار كل تقرير وكل عملية قراءة/كتابة.
6. تغطية التقارير المالية والتشغيلية: لوحة التحكم، التدفقات، الدخل، المقارنة، المدفوعات، المصروفات، الديزل، الدفتر، القيود، حسابات المستفيدين والعاملين والشركاء.
7. إبقاء النسخ والاستعادة الكاملين معطلين على قاعدة مشتركة إلى أن يكتمل تصدير/استيراد خاص بالمحطة واختبار الاستعادة.

- الدفعة 5: إعادة تشغيل الاختبارات والتحليل والبناء على آخر commit، ثم مراجعة النتائج الفعلية.

## سجل التنفيذ — الدفعة الأولى من تطبيق الطلبات

بدأ التنفيذ البرمجي على الفرع المستهدف، وأضيفت أول شريحة رأسية للمزامنة الآمنة:

- أضيف جدول ربط `sync_entity_links` لربط الهوية العالمية بالسجل المحلي داخل المحطة، مع قيود تمنع تكرار الهوية أو ربطها بسجلين داخل المحطة نفسها.
- أصبح الخادم يطبق إنشاء/تعديل/حذف المستفيدين على جدول الأعمال، ويأخذ `station_id` من JWT فقط، ويتجاهل `id` المحلي القادم من الجهاز.
- تُنفذ كتابة سجل الأعمال وسجل الحدث وتحديث إصدار الكيان داخل SAVEPOINT ضمن معاملة الدفعة؛ فشل التطبيق يعيد الحدث إلى نقطة الحفظ ولا ينتج عنه `accepted` أو تقدم للإصدار.
- المجالات الأخرى، ومنها المدفوعات والقيود المالية، ترفض حالياً برسالة واضحة ولا تحصل على إقرار نجاح حتى تُنفذ معالجاتها المتخصصة.
- التعديلات غير الصفرية على الرصيد الافتتاحي/المرحّل/رصيد الديزل للمستفيد ترفض حتى يضاف معالج محاسبي يعيد بناء القيود والأرصدة.
- منع إقرار الأحداث القديمة المسجلة `accepted` من النسخة السابقة كـ duplicate ما لم يوجد إثبات ربط بسجل أعمال حقيقي؛ تُعاد للمراجعة بدلاً من الإقرار الكاذب.
- أضيفت اختبارات للمستفيدين (إنشاء/تعديل/تكرار/تعارض/فشل التطبيق) ولرفض الأحداث المالية غير المنفذة، واختبارات عزل للتقارير المنفذة الخمسة.

### ما لم يكتمل بعد

- لا يزال تطبيق المزامنة على بقية المجالات غير منفذ، ولا سيما السقايات والجلسات والطابور والدفعات والقيود المالية.
- لم يُنقل بعد Repository التطبيق الأساسي إلى وضع Server-connected؛ ما زالت شاشات Flutter تستخدم SQLite المحلية كمصدر تشغيل، والمزامنة الحالية مسار نقل منفصل. لا يجوز وصف هذا بأنه توحيد كامل لمصدر البيانات.
- التقارير الـ19 الأخرى لا تزال غير منفذة وتستجيب `501 REPORT_NOT_IMPLEMENTED`؛ التقارير الخمسة المنفذة تبقى مقيدة بالمحطة في استعلاماتها، وأضيفت تغطية اختبارية لها.
- يلزم تشغيل `dart format`, `dart analyze`, واختبارات الخادم وFlutter Analyze/Tests وبناء APK على رأس الفرع بعد هذه التغييرات. لا يوجد اعتماد نجاح حتى تظهر نتائج CI الفعلية.

   - payWorker() وpayPartner() يضيفان أيضاً صفاً تابعاً في worker_transactions أو partner_transactions داخل المعاملة نفسها؛ لذلك يجب عدم توسيع معالج قبض المستفيد إليهما ضمنياً.

2. **مخطط العمليات**
   - payments يحتوي station_id وحقول الطرف الثلاثة beneficiary_id / partner_id / worker_id مع CHECK يفرض طرفاً واحداً فقط، ومراجع إلزامية إلى طريقة الدفع والصندوق.
   - sync_global_identities يمنح UUID ثابتاً للسجلات المحلية، بما فيها payments وjournal_entries وjournal_lines وcashboxes وpayment_methods وbeneficiary_manual_debts وdiesel_movements.
   - مخطط Outbox المحلي sync_queue يملك event_id فريداً جزئياً، وbase_version وdevice_id وstatus وبيانات المحاولة/الخطأ. توجد Inbox وmetadata وentity versions محلية.
   - مشغلات SQLite تسجل تغييرات payments والصناديق والقيود وبنود القيود والمديونيات اليدوية وحركات الديزل وغيرها في sync_change_log.

3. **حدود المزامنة الخادمية الحالية**
   - _syncPush يثبت event_id على مستوى المحطة ويقارن الحمولة/المصدر عند إعادة الاستخدام، ثم ينفذ معالج المجال داخل SAVEPOINT قبل إرجاع accepted.
   - _applySyncBusinessEvent() لا يدعم حالياً إلا beneficiaries؛ المجالات المالية الأخرى ترفض عمداً ولا تحصل على accepted.
   - POST /api/v1/payments موجود كمسار مباشر، لكنه لا يفرض مفتاح عملية من العميل ولا يملك قيداً مستقلاً يضمن إعادة نتيجة العملية ذاتها عند إعادة طلب HTTP بعد انقطاع الاستجابة. لا يُعد هذا بديلاً آمناً عن معالج Outbox ذي idempotency.
   - _paymentCreateUnsafe() ينشئ الدفعة ويزيد رصيد الصندوق ويكتب قيد اليومية داخل _atomic()، ويتحقق من ملكية المراجع الأساسية. يجب أن يعاد استخدام قواعد المجال بعد توحيد عقد العملية، لا نسخ منطق محاسبي ثانٍ مختلف.

4. **مشكلة السجلات التابعة التي يجب حلها قبل تفعيل قبض المستفيد**
   - كتابة القبض محلياً تنتج أكثر من أثر: payments، تحديث cashboxes.current_balance، journal_entries، وjournal_lines، وقد تنتج سجلات تدقيق/تنبيه.
   - مشغلات التتبع الحالية تلتقط جداول مالية عديدة؛ إرسال كل صف تابع كحدث مستقل بالتوازي مع أمر القبض قد يكرر القيد أو يحدّث الصندوق مرتين.
   - يجب أن تكون وحدة المزامنة **أمر قبض واحداً** بهوية عملية ثابتة، ويعيد الخادم إنشاء كل الآثار التابعة مرة واحدة في معاملة واحدة. يجب تمييز الآثار المشتقة ومنع تحويلها إلى أوامر مالية مستقلة في Outbox، مع عدم إسقاط تغييرات المستخدم المستقلة.
   - لا يجوز أن تعني حالة accepted مجرد حفظ الحدث؛ يجب أن تعني إنشاء الدفعة والأثر على الصندوق والقيد المحاسبي وروابط الهوية كلها بنجاح ذري.

### شروط تنفيذ معالج قبض المستفيد

- استخدام UUID ثابت للعملية، وربط المستفيد وطريقة الدفع والصندوق بهويات عالمية؛ لا ترسل أرقام SQLite المحلية بوصفها معرفات مشتركة.
- اشتقاق station_id وuser_id والدور من JWT فقط، والتحقق من ملكية المستفيد وطريقة الدفع والصندوق قبل أي كتابة.
- إضافة قيد Idempotency خادمي فريد على (station_id, event_id) أو مفتاح أمر مكافئ، مع مقارنة الحمولة canonical: إعادة الطلب المطابقة تعيد نتيجة العملية الأصلية؛ وإعادة استخدام المفتاح بحمولة مختلفة ترفض.
- إنشاء صف payments وتحديث الصندوق وقيود اليومية وروابط الهوية وسجل الحدث ضمن معاملة ذرية واحدة؛ أي فشل يعيد كل الآثار ولا يترك accepted.
- حفظ الأمر المحلي والعملية المحاسبية المحلية/Outbox في معاملة SQLite واحدة، مع بقاء الأمر pending عند انقطاع الشبكة، وعدم إنشاء أمر جديد عند retry.
- عدم تطبيق fallback محلي على أخطاء HTTP أو رفض الصلاحية؛ fallback مسموح فقط لانقطاع النقل، مع إظهار أن الرصيد محلي غير مؤكد.
- اختبار: نجاح القبض، مبلغ غير صالح، طرف غير تابع للمحطة، طريقة دفع/صندوق من محطة أخرى، JWT مفقود/دور غير مسموح، إعادة إرسال الحدث نفسه، إعادة استخدام event_id بحمولة مختلفة، فشل DB/rollback، انقطاع قبل الإرسال وبعد تطبيق الخادم وقبل وصول الرد، توافق السجلات القديمة، وثبات رصيد الصندوق وتوازن القيد وعدم تكرارهما.
- لا يبدأ تنفيذ الكود المالي قبل تصميم آلية منع التقاط الآثار المشتقة من مشغلات Outbox، وتحديد كيفية إعادة نتيجة القبض عند retry.
