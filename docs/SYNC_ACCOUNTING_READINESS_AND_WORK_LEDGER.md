## 1. المعمارية وقواعد البيانات — الحالة المعتمدة

- تطبيق Flutter يحتفظ بقاعدة SQLite محلية.
- Shelf server يحتفظ بقاعدة SQLite يفتحها عبر إعداد `SAQIA_DB`.
- مزامنة Offline-First تنقل أحداث/أوامر بين المحلي والخادم؛ لا يعني ذلك أن الهاتف والخادم يفتحان ملف SQLite نفسه.
- عند توفر الاتصال، الخادم هو جهة التحقق وتطبيق أوامر الأعمال المركزية؛ لا يجوز اعتماد الرصيد المحلي كحقيقة نهائية.
- لا تكتب الأرصدة أو القيود المحاسبية كقيم موثوقة قادمة من العميل؛ الخادم يعيد احتسابها داخل معاملة ذرية.
- Firebase/Firestore ليس مخزن المزامنة الفعلي في هذه المعمارية الحالية.

**تنبيه توثيقي:** وثيقة القرار المعماري تحتوي وصفاً تاريخياً لمسارات المزامنة يحتاج تحديثاً؛ الكود الحالي الذي تمت مراجعته يحتوي `POST /api/v1/sync/events` و`GET /api/v1/sync/inbox`. عند تعديل الوثيقة المعمارية، حدّث الوصف القديم بدليل من Router وSyncService، ولا تغيّر قرار المعمارية دون قرار صريح.

## 2. ما هو جاهز أو موجود بالفعل — لا تعِد تنفيذه دون دليل على وجود خلل

الحالة هنا تعني أن التنفيذ أو التوثيق موجود في المصدر الذي تمت مراجعته. لا تعني تلقائياً أن كل مسار إنتاجي أو كل جهاز تم اختباره.

| Outbox/إرسال | خدمة إرسال أحداث المزامنة | `lib/services/sync_service.dart` | موجود |
| Inbox/استقبال | تطبيق الأحداث الواردة على قاعدة الجهاز | `lib/services/sync_inbox_applier.dart` | موجود |

### ممنوع اعتبار البنود التالية مكتملة لمجرد وجودها في `_syncEntityTypes`

القائمة المسجلة للأنواع ليست دليلاً على وجود handler. يجب أن يوجد لكل نوع:
- مصدر إنشاء/تعديل محلي معروف.
- حدث Outbox صالح.
- handler صريح في الخادم.
- تحقق من station ownership والهوية والصلاحيات.
- معاملة ذرية للآثار.
- سياسة replay/idempotency والتعارض.
- اختبار نجاح وفشل وعكس مالي عند الحاجة.

## 3. المتبقيات — ترتيب التنفيذ الإلزامي

لا تنفذ أكثر من مجال واحد في الدفعة الواحدة. ابدأ بالبند الأول المفتوح فقط، ثم حدّث الحالة وانتقل بعد التحقق.

### P0 — ضبط عقد الأحداث والآثار المحاسبية التابعة

**المشكلة:** العملية الواحدة قد تغيّر السقاية والقيود وحركات العامل/الشريك والديزل والجداول التابعة. قد يرسل العميل أحداثاً لكل الجداول بينما يعيد الخادم توليد بعض الآثار، أو يرفض أحداثاً تابعة لا يملك لها handler.

المطلوب:
- [ ] توثيق مصفوفة «أمر العمل الأصلي → الجداول التي يكتبها العميل محلياً → الجداول التي ينشئها الخادم».
- [ ] تحديد مالك وحيد لإنشاء كل قيد/حركة تابعة.
- [ ] منع إرسال journal_entries/journal_lines أو الحركات التابعة كأوامر مستقلة عندما ينشئها handler الأصلي.
- [ ] التأكد أن تغيير Outbox لا يفقد الأحداث المستقلة فعلاً.
- [ ] اختبار عملية مركبة وإعادة إرسالها مرتين، والتحقق من عدم مضاعفة أي رصيد أو قيد.
- [ ] اختبار فشل جزئي يثبت rollback الكامل أو retry آمن.

**قبول P0:** حدث أعمال واحد يؤدي إلى نتيجة محاسبية واحدة متوازنة؛ إعادة الإرسال لا تكرر الأثر؛ لا تبقى أحداث تابعة مرفوضة في Outbox بلا معالجة.

## 4. مصفوفة التتبع الإلزامية لكل عملية

يجب ملء صف لكل عملية كتابة/تعديل/إلغاء قبل اعتماد المجال:

| العملية | Local table(s) | Repository/service | Outbox entity/action | Server handler | الآثار التابعة | Reversal | الاختبار |
|---|---|---|---|---|---|---|---|
| مثال: إنشاء سقاية | irrigations + ... | recordIrrigation | يحدد بعد التحقق | يحدد بعد التحقق | journal/worker/partner/diesel | حسب العقد | unit + server + e2e |
| مثال: إلغاء قبض | payments + ... | payment cancellation service | update/cancel | handler صريح | cashbox + journal | مطلوب | replay + reversal |

**لا تضع «مدعوم» لمجرد وجود اسم الجدول في قائمة الأنواع.** لا يكتمل الصف إلا بعد تتبع الكود من بداية العملية إلى أثر الخادم واختبارها.

---

## 5. قواعد الإلغاء والعكس المحاسبي

1. لا حذف فعلي للعمليات المالية أو المخزنية المرحلة.
2. الإلغاء حالة/حدث صريح، مع سبب ووقت وهوية المنفذ.
3. القيد العكسي قيد جديد مرتبط بالقيد الأصلي؛ لا تعدّل القيد الأصلي أو تمحوه.
4. مجموع المدين يساوي مجموع الدائن في الأصل والعكس.
5. عكس حركة الصندوق/المخزون يجب أن يطابق العملية الأصلية، لا قيمة يرسلها العميل دون تحقق.
6. كل إلغاء له idempotency: محاولة ثانية لا تنشئ قيداً أو حركة ثانية.
7. إذا فشل أي جزء، تتراجع المعاملة كاملة.
8. لا تسمح بإلغاء أصل له آثار لاحقة غير معالجة؛ عالج الاعتماديات بترتيب عكسي.

## 6. شروط إعلان نجاح أي دفعة

لا تسجل المهمة «مكتملة» إلا بعد توفر جميع ما يلي:

- [ ] مراجعة الكود قبل التعديل وإثبات عدم تكرار العمل.
- [ ] تنفيذ العميل والخادم ضمن نطاق واضح.
- [ ] اختبارات نجاح وفشل وصلاحيات وعزل محطة.
- [ ] اختبارات replay/idempotency والتعارض.
- [ ] اختبار الأثر المالي: الأرصدة، الصندوق، الأستاذ، المخزون عند الحاجة.
- [ ] Flutter analyze ناجح.
- [ ] الاختبارات المحددة ناجحة، مع ذكر العدد/الأسماء.
- [ ] Server tests ناجحة.
- [ ] Android Release build ناجح وArtifact موجود، إذا كان التغيير يؤثر في التطبيق.
- [ ] GitHub Actions النهائية خضراء؛ لا تعتمد على حالة قيد التشغيل أو نتيجة قديمة.
- [ ] توثيق ما تغير وما لم يتغير، وSHA الالتزام.
- [ ] تحديث حالة المهمة أدناه فقط بعد اكتمال الأدلة.

أي بند ناقص يعني أن الحالة **قيد التنفيذ** أو **غير متحقق**، وليس مكتمل.

## 8. سجل ما لم يتم إثباته في إعداد هذه الوثيقة

- لم يتم تشغيل Flutter Analyze أو Flutter Test أو Server Tests أثناء إعداد هذا السجل.
- لم يتم تنفيذ اختبار جهازين حقيقيين في هذه الجولة.
- لم يتم إثبات أن كل CRUD في كل شاشة يمر عبر Outbox.
- لم يتم إثبات أن كل نوع في `_syncEntityTypes` له handler مكتمل.
- لم يتم التحقق من جميع عمليات حذف/إلغاء الخدمات المحاسبية واحدةً واحدةً؛ يلزم إكمال المصفوفة في P0 ثم كل مجال.
- نتائج CI السابقة لا تُستخدم كدليل على نجاح HEAD الحالي إلا بعد فحص Actions المرتبطة به.

**الخلاصة التنفيذية:** لا تعِد تنفيذ Outbox/Inbox أو مزامنة المصروفات والتحويلات والديزل من الصفر. ابدأ بمراجعة عقد الأحداث والآثار التابعة P0، ثم نفّذ مجالاً واحداً في كل دفعة، ولا تنتقل قبل تسجيل نجاحه هنا.
