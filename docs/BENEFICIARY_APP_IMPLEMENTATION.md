# سجل تنفيذ تطبيق المستفيد داخل تطبيق المحطة

> هذه الوثيقة سجل تراكمي. أضف كل دفعة لاحقة بتاريخها وملفاتها واختباراتها، ولا تستبدل السجل السابق.

## القرار المعتمد
- تطبيق المستفيد سيكون **داخل تطبيق المحطة نفسه**، وليس APK منفصلًا.
- طريقة دخول المستفيد: **اسم مستخدم وكلمة مرور**.
- يجب الإبقاء على مسار دخول إدارة المحطة الحالي دون تغيير سلوكه.
- لا يُسمح للمستفيد بتسجيل سقاية أو دفعة مالية أو تعديل بيانات المحطة. يقتصر التطبيق على عرض بياناته وطلباته والوظائف التي تُعتمد لاحقًا.
- مصدر الحقيقة للأرصدة هو منطق المحاسبة المعتمد في التطبيق الرئيسي، وليس نسخة حساب مستقلة قد تختلف عنه.

## الدفعة 1 — فحص الوضع الحالي وتحديد نقاط الدمج

### النطاق
فحص نقطة تشغيل Flutter، وواجهة المستفيد الحالية، وعميل API، وخدمة المصادقة، وخادم API، ومخطط قاعدة البيانات، وصيغة رصيد المستفيد. لا تتضمن هذه الدفعة تعديل منطق المحاسبة أو بيانات SQLite.

### نتائج الفحص

1. **نقطة تشغيل التطبيق**
   - `lib/main.dart` يشغّل `SaqiaApp`.
   - `SaqiaApp` في `lib/features/app.dart` يستخدم `MaterialApp` واحدًا، ويبدأ حاليًا من `AdminLoginPage`.
   - واجهة المستفيد الحالية ليست موصولة بنقطة الدخول؛ البحث عن `BeneficiaryApp` أظهر تعريفها في `lib/features/beneficiary_app.dart` فقط، ولم يظهر استدعاء تشغيلي لها في التطبيق الرئيسي.

2. **واجهة المستفيد الموجودة**
   - `lib/features/beneficiary_app.dart` تحتوي تسجيل دخول برقم الهاتف ورمز تحقق، ثم صفحة رئيسية تعرض بيانات المستفيد والرصيد وطلبات الحجز والإشعارات.
   - هذه الواجهة تنشئ `MaterialApp` مستقلًا، ولذلك لا تحقق قرار المستخدم بدمجها داخل التطبيق الرئيسي كما هي. الأنسب إعادة استخدامها كشاشات داخل MaterialApp الحالي، مع مشاركة الثيم واللغة والتنقل.

3. **عميل الاتصال**
   - `lib/api/api_client.dart` يحتوي `ApiClient` و`BeneficiaryApi`.
   - عنوان الخادم يُمرر إلى المنشئ، ولا توجد في هذا العميل حاليًا آلية ظاهرة لاختيار عنوان API للمستفيد من إعدادات التطبيق.
   - ترويسة `X-Station-Id` مثبتة حاليًا على القيمة `1`؛ يجب عدم تعميم ذلك عند تنفيذ الدخول، بل ربط الجلسة بالمحطة المصرح بها والتحقق من الملكية على الخادم.

4. **المصادقة الحالية**
   - `lib/api/auth_service.dart` يعتمد رقم الهاتف ورمزًا سداسيًا.
   - `server/lib/server.dart` يعرّف المسارين `POST /api/v1/beneficiary/request-code` و`POST /api/v1/beneficiary/session`.
   - بعد الدخول يصدر الخادم JWT من نوع beneficiary ويخزن بصمة الجلسة في `beneficiary_sessions`، وتتحقق مسارات المستفيد من نوع الجلسة وصلاحيتها.
   - هذا المسار لا يحقق اسم المستخدم وكلمة المرور المطلوبين، وسيحتاج استبدالًا/توسعة مدروسة، لا تغيير واجهة Flutter وحدها.

5. **مخطط بيانات المستفيد**
   - جدول `beneficiaries` في `assets/db/001_initial.sql` يتضمن الاسم والهاتف والعنوان والمنطقة والحالة والأرصدة، ولا يحتوي اسم مستخدم أو كلمة مرور.
   - جدولَا `beneficiary_auth_codes` و`beneficiary_sessions` يضافان عبر ترحيلات قاعدة البيانات، وليسَا حقولًا في جدول المستفيد.
   - لا توجد في المخطط الأساسي بيانات اعتماد باسم مستخدم وكلمة مرور للمستفيد. يجب تصميم تخزين بيانات الاعتماد قبل بناء شاشة الدخول.

6. **الرصيد**
   - الصيغة المرجعية في التطبيق الرئيسي هي `lib/domain/accounting/balance_sql.dart` عبر `BalanceSql.beneficiary`.
   - الصيغة تشمل الرصيد الافتتاحي والمرحّل والسقايات غير الملغاة وسلف الديزل اليدوية والدفعات المرحّلة وتسليم الديزل عندما يكون إعداد التسليم كرصيد مالي مفعّلًا.
   - الخادم لديه استعلام مستقل في `_beneficiaryAccount` داخل `server/lib/server.dart`. رغم تقارب الصيغة، فإن وجود نسختين مستقلتين خطر انحراف محاسبي؛ يجب اختبار تطابق الخادم مع صيغة التطبيق الرئيسي، بما فيها الحالات الحدية، قبل عرض الرصيد للمستفيد.

7. **الصلاحيات**
   - مسارات المستفيد الحالية محمية بمعالج `_beneficiaryAuth` وتربط الجلسة بمعرف مستفيد واحد.
   - يجب الحفاظ على عزل المستفيد: لا يقبل الخادم معرف مستفيد يرسله العميل لاختيار حساب آخر؛ يستخرج المعرف من الجلسة الموثقة، ويجب التحقق من المحطة أيضًا.

### قرارات التصميم المقترحة للدفعة التالية

- إضافة مدخل واضح «دخول المستفيد» إلى تجربة الدخول الحالية، مع بقاء دخول الإدارة كما هو. لا نضيف تطبيق Flutter جذريًا ثانيًا ولا `MaterialApp` ثانيًا.
- تحويل شاشة المستفيد إلى صفحات داخل التطبيق الرئيسي، مع إعادة استخدام خدمات API الموجودة بعد تحديث المصادقة.
- إنشاء بيانات اعتماد مستقلة للمستفيدين (يفضل جدولًا مخصصًا مرتبطًا بـ `beneficiary_id` و`station_id` واسم مستخدم فريد ضمن نطاق المحطة)، بدل تخزين كلمة المرور كنص أو خلطها بحقول الملف الشخصي.
- تخزين كلمة المرور باستخدام خوارزمية اشتقاق كلمات مرور بطيئة ومملحة ومعتمدة (مثل Argon2id أو bcrypt أو PBKDF2 بإعدادات قوية)، وليس SHA-256 منفردًا.
- إنشاء/تغيير بيانات دخول المستفيد من حساب إداري مخوّل، وعدم فتح التسجيل الذاتي لحسابات المستفيدين.
- إضافة تحديد محاولات الدخول، ورسائل خطأ لا تكشف هل اسم المستخدم موجود، وانتهاء الجلسة وإمكانية إلغائها، وعدم إرجاع أسرار المصادقة في API.
- جعل كل طلب API مقيدًا بالمستفيد الموثق والمحطة، واختبار منع الوصول إلى بيانات مستفيد آخر.
- اعتماد صيغة رصيد واحدة أو اختبار تكافؤ آلي بين SQL الخادم و`BalanceSql.beneficiary` قبل إطلاق الميزة.

## الدفعة 2 — اعتماد آلية إنشاء بيانات الدخول وتصميمها

### قرار المستخدم
- المدير هو من ينشئ اسم المستخدم وكلمة المرور لكل مستفيد يدويًا.
- لا ينشئ النظام بيانات دخول تلقائيًا عند إضافة المستفيد.
- لا يوجد تسجيل ذاتي أو تفعيل حساب بواسطة المستفيد.
- تبقى إضافة المستفيد العادية ممكنة دون إجبار المدير على إنشاء بيانات دخول في اللحظة نفسها؛ ويمكن ربط بيانات الدخول لاحقًا من إدارة المستفيدين.

### تدفق العمل المعتمد
1. يدخل المدير إلى حساب الإدارة بالطريقة الحالية.
2. يفتح ملف مستفيد موجودًا، ثم يختار «إنشاء بيانات دخول» أو «تغيير بيانات الدخول».
3. يحدد اسم مستخدم وكلمة مرور أولية، ويؤكد كلمة المرور قبل الحفظ.
4. يتحقق الخادم من صلاحية المدير ومن أن المستفيد تابع للمحطة نفسها، ومن عدم استخدام اسم المستخدم لمستفيد آخر في نطاق المحطة.
5. يحفظ الخادم بصمة كلمة المرور فقط باستخدام خوارزمية مخصصة لكلمات المرور مع salt وإعدادات قوية؛ لا تُحفظ كلمة المرور الأصلية ولا تعاد في استجابة API.
6. يعرض التطبيق بيانات الدخول للمدير مرة واحدة بعد نجاح الإنشاء كي يسلّمها للمستفيد. بعد إغلاق العرض لا يستطيع المدير استرجاع كلمة المرور؛ يستطيع فقط تعيين كلمة مرور جديدة.
7. يستطيع المدير تعطيل دخول المستفيد أو إعادة تفعيله، كما يؤدي تغيير كلمة المرور أو تعطيل الحساب إلى إبطال الجلسات السابقة.

### تصميم البيانات والصلاحيات
- جدول مستقل لبيانات اعتماد المستفيد، مرتبط بمعرف المستفيد والمحطة، مع قيد فريد لاسم المستخدم ضمن المحطة.
- تخزين حالة التفعيل، بصمة كلمة المرور، وقت الإنشاء والتحديث، ومعرّف المدير الذي أنشأ أو غيّر بيانات الدخول عند توفر بنية التدقيق المناسبة.
- جميع عمليات الإنشاء والتغيير والتعطيل وإعادة التفعيل محمية بدور المدير `manager` على الخادم؛ إخفاء الأزرار في Flutter ليس بديلًا عن فحص الصلاحية بالخادم.
- لا يقبل الخادم `beneficiary_id` من العميل لتحديد حساب صاحب الجلسة بعد الدخول؛ يستخرج هوية المستفيد والمحطة من بيانات الاعتماد/الجلسة الموثقة.
- يجب أن تكون رسائل فشل الدخول عامة، مع تحديد محاولات الدخول، وعدم كشف ما إذا كان اسم المستخدم موجودًا.
- لا يُعاد hash كلمة المرور أو أي سر مصادقة ضمن أي endpoint إداري أو خاص بالمستفيد.

### نطاق التنفيذ القادم
1. مراجعة ترحيلات SQLite الحالية، واعتماد مكتبة hashing متوافقة فعليًا مع بيئة الخادم قبل كتابة التنفيذ.
2. إضافة migration قابلة لإعادة التشغيل بأمان لإنشاء جدول بيانات الاعتماد، دون تعديل سجلات المستفيدين الحالية أو الأرصدة.
3. إضافة مسارات API إدارية لإنشاء بيانات الدخول وتغييرها وتعطيلها/إعادة تفعيلها، ومسار دخول باسم المستخدم وكلمة المرور.
4. تحديث واجهة إدارة المستفيدين لإدخال بيانات الدخول يدويًا، وإظهار كلمة المرور الأولية مرة واحدة فقط.
5. تحويل واجهة المستفيد الحالية من دخول الهاتف/الرمز إلى دخول اسم المستخدم/كلمة المرور، ودمجها في `MaterialApp` الرئيسي دون إنشاء تطبيق جذري ثانٍ.
6. إضافة اختبارات عزل المحطة والمستفيد، والصلاحيات، وتكرار اسم المستخدم، وكلمات المرور الخاطئة، وإبطال الجلسات، وتكافؤ الرصيد.

### ما لم يتغير في هذه الدفعة
- لم تُعدّل ملفات التطبيق أو الخادم أو مخطط قاعدة البيانات.
- لم تُنشأ بيانات دخول لأي مستفيد ولم تتغير بيانات أي حساب.
- لم يُمس منطق المحاسبة أو الأرصدة.
- لم يُجر أي دمج إلى `main`.

### الاختبارات والحالة
- مراجعة ساكنة لواجهة المستفيد الحالية وخدمة المصادقة ونقطة دخول التطبيق ومسارات API الإدارية.
- لم تُشغّل اختبارات أو بناء Flutter؛ هذه الدفعة اعتماد قرار وتصميم فقط.
- الحالة: **تم تثبيت قرار إنشاء بيانات الدخول يدويًا بواسطة المدير؛ التنفيذ البرمجي لم يبدأ بعد**.


## الدفعة 3 — تثبيت ترتيب التنفيذ المحلي أولًا

### قرار التنفيذ
- يبدأ التنفيذ داخل نسخة SQLite المحلية الحالية، ثم يُضاف اتصال API بعد اكتمال الواجهات والمنطق المحلي واختبارهما.
- خدمة المصادقة المحلية ستكون طبقة مستقلة باسم واضح، ولا تستدعي ApiClient ولا تستخدم جلسات OTP الحالية. عند إضافة API لاحقًا تُضاف طبقة تنفيذ أخرى خلف واجهة خدمة مشتركة بدل خلط التخزين المحلي والاتصال الشبكي.
- لا يُنشأ حساب دخول تلقائيًا عند إضافة مستفيد؛ المدير ينشئه يدويًا من ملف المستفيد بعد التحقق من صلاحياته.
- تظل شاشة قفل الإدارة ومسار AdminLoginPage الحاليان مستقلين. دخول المستفيد لا يفتح AdminShell ولا يرث صلاحيات المدير.

### نتائج الفحص الإضافي
1. قاعدة SQLite الحالية إصدارها 19، والترقية تمر عبر _upgrade، والجداول المساعدة تُنشأ أيضًا عبر _createHelpers. أي إضافة مستقبلية يجب أن ترفع الإصدار إلى 20 وتكون قابلة للتنفيذ مرة واحدة على قواعد الإصدار 19، مع اختبار قاعدة قديمة تحتوي سجلات فعلية.
2. يوجد AuthService في lib/api/auth_service.dart لكنه خاص بـ API وOTP؛ لن نعيد استخدامه للمصادقة المحلية أو نغيّر سلوكه ضمن الدفعة المحلية.
3. lib/features/beneficiary_app.dart ما زالت تنشئ MaterialApp مستقلًا وتستخدم رقم الهاتف/OTP. يلزم تحويلها إلى صفحات عادية ضمن جذر SaqiaApp، وعدم تركيب جذر Flutter ثانٍ.
4. نقطة SaqiaApp الرئيسية في lib/features/app.dart تبدأ من AdminLoginPage، وهي شاشة قفل محلية للإدارة. يجب إضافة مدخل مستقل لدخول المستفيد دون تغيير تدفق الإدارة الحالي.
5. مستودع StationRepository يقرأ المستفيدين ويضيفهم ويعدلهم، ويحتوي تدقيقًا للعمليات. لا يجوز وضع بيانات الاعتماد في beneficiaries أو تمرير حقولها عبر تحديث ملف المستفيد العام.
6. الاعتمادية crypto الحالية توفر SHA/HMAC فقط؛ لا تكفي وحدها لتخزين كلمات المرور. تمت مراجعة خيارات Dart المنشورة: cryptography_plus يذكر Argon2id، وhashlib يذكر Argon2id وPBKDF2 ويعمل على منصات Flutter المختلفة. لم تُضف أي حزمة ولم يُعتمد تنفيذ hashing قبل التحقق من API الفعلية، توافقها مع قيود المنصات وإصدارات SDK، وتشغيل اختبارات حتمية لها. يمنع استخدام SHA-256 منفردًا أو كتابة KDF يدويًا في التطبيق.

### مخطط الترحيل المقترح — لا يزال غير منفذ
- رفع إصدار SQLite من 19 إلى 20.
- إنشاء جدول مستقل باسم beneficiary_credentials يتضمن id, station_id, beneficiary_id, username_normalized, password_hash, password_salt أو تمثيلًا ذاتيًا للـ KDF، kdf_name, kdf_parameters, active, created_at, updated_at, created_by, updated_by.
- قيد فريد على (station_id, username_normalized)، وقيد فريد على (station_id, beneficiary_id) لمنع أكثر من حساب للمستفيد الواحد في المحطة.
- ربط السجل بالمستفيد بمفتاح أجنبي، وإضافة فهارس للاستعلام. لا تُضاف كلمة المرور أو hash إلى جدول beneficiaries.
- لا تُنشأ بيانات اعتماد للسجلات القديمة ولا تتغير أرصدتها أو حركاتها. الترحيل يضيف بنية فارغة فقط.
- يجب أن تكون عمليات إنشاء/تغيير/تعطيل بيانات الاعتماد ضمن معاملات SQLite، مع تدقيق الحدث دون تسجيل كلمة المرور أو hash أو salt أو أي سر.

### ضوابط الصلاحيات المحلية
- في المرحلة المحلية، لا تكفي إخفاء زر الإدارة. يجب أن تستقبل خدمة إدارة بيانات الاعتماد هوية المستخدم الإداري النشطة ودوره بعد اجتياز بوابة AdminLoginPage، وتتحقق من role == manager داخل كل عملية كتابة قبل تعديل الجدول.
- لا تسمح صفحات المستفيد باستدعاء خدمة إدارة بيانات الاعتماد، ولا تعتمد هوية المستفيد من حقل يرسله المستخدم؛ تستخرجها من جلسة محلية موثقة محفوظة بطريقة آمنة.
- يجب أن تكون جلسة المستفيد منفصلة عن جلسة الإدارة، وأن تُمسح عند تسجيل الخروج أو تعطيل الحساب أو تغيير كلمة المرور.

### شروط بدء التعديل البرمجي
- اعتماد حزمة KDF بعد فحص توثيق API والإصدارات واختبارها على Android والأنظمة التي يدعمها التطبيق.
- فحص موضع شاشة إدارة المستفيدين داخل app.dart وتحديد callback آمن يمرر هوية المدير الحالية؛ لا نضيف شاشة إدارة بديلة مكررة.
- تنفيذ الترحيل وخدمة المصادقة واختبارات DB أولًا، ثم توصيل الواجهات.
- تشغيل flutter pub get, flutter analyze, flutter test وبناء Android إن توفرت بيئة Flutter. لا تعتبر مراجعة GitHub أو قراءة المصدر بديلًا عن التشغيل.
