# سجل تنفيذ تطبيق المستفيد داخل تطبيق المحطة

> هذه الوثيقة سجل تراكمي. أضف كل دفعة لاحقة بتاريخها وملفاتها واختباراتها، ولا تستبدل السجل السابق.

## القرار المعتمد
- تطبيق المستفيد سيكون **داخل تطبيق المحطة نفسه**، وليس APK منفصلًا.
- طريقة دخول المستفيد: **اسم مستخدم وكلمة مرور**.
- يجب الإبقاء على مسار دخول إدارة المحطة الحالي دون تغيير سلوكه.
- لا يُسمح للمستفيد بتسجيل سقاية أو دفعة مالية أو تعديل بيانات المحطة. يقتصر التطبيق على عرض بياناته وطلباته والوظائف التي تُعتمد لاحقًا.
- مصدر الحقيقة للأرصدة هو منطق المحاسبة المعتمد في التطبيق الرئيسي، وليس نسخة حساب مستقلة قد تختلف عنه.

## الدفعة 1 — فحص الوضع الحالي وتحديد نقاط الدمج

### النطاق
فحص نقطة تشغيل Flutter، وواجهة المستفيد الحالية، وعميل API، وخدمة المصادقة، وخادم API، ومخطط قاعدة البيانات، وصيغة رصيد المستفيد. لا تتضمن هذه الدفعة تعديل منطق المحاسبة أو بيانات SQLite.

### نتائج الفحص

1. **نقطة تشغيل التطبيق**
   - `lib/main.dart` يشغّل `SaqiaApp`.
   - `SaqiaApp` في `lib/features/app.dart` يستخدم `MaterialApp` واحدًا، ويبدأ حاليًا من `AdminLoginPage`.
   - واجهة المستفيد الحالية ليست موصولة بنقطة الدخول؛ البحث عن `BeneficiaryApp` أظهر تعريفها في `lib/features/beneficiary_app.dart` فقط، ولم يظهر استدعاء تشغيلي لها في التطبيق الرئيسي.

2. **واجهة المستفيد الموجودة**
   - `lib/features/beneficiary_app.dart` تحتوي تسجيل دخول برقم الهاتف ورمز تحقق، ثم صفحة رئيسية تعرض بيانات المستفيد والرصيد وطلبات الحجز والإشعارات.
   - هذه الواجهة تنشئ `MaterialApp` مستقلًا، ولذلك لا تحقق قرار المستخدم بدمجها داخل التطبيق الرئيسي كما هي. الأنسب إعادة استخدامها كشاشات داخل MaterialApp الحالي، مع مشاركة الثيم واللغة والتنقل.

3. **عميل الاتصال**
   - `lib/api/api_client.dart` يحتوي `ApiClient` و`BeneficiaryApi`.
   - عنوان الخادم يُمرر إلى المنشئ، ولا توجد في هذا العميل حاليًا آلية ظاهرة لاختيار عنوان API للمستفيد من إعدادات التطبيق.
   - ترويسة `X-Station-Id` مثبتة حاليًا على القيمة `1`؛ يجب عدم تعميم ذلك عند تنفيذ الدخول، بل ربط الجلسة بالمحطة المصرح بها والتحقق من الملكية على الخادم.

4. **المصادقة الحالية**
   - `lib/api/auth_service.dart` يعتمد رقم الهاتف ورمزًا سداسيًا.
   - `server/lib/server.dart` يعرّف المسارين `POST /api/v1/beneficiary/request-code` و`POST /api/v1/beneficiary/session`.
   - بعد الدخول يصدر الخادم JWT من نوع beneficiary ويخزن بصمة الجلسة في `beneficiary_sessions`، وتتحقق مسارات المستفيد من نوع الجلسة وصلاحيتها.
   - هذا المسار لا يحقق اسم المستخدم وكلمة المرور المطلوبين، وسيحتاج استبدالًا/توسعة مدروسة، لا تغيير واجهة Flutter وحدها.

5. **مخطط بيانات المستفيد**
   - جدول `beneficiaries` في `assets/db/001_initial.sql` يتضمن الاسم والهاتف والعنوان والمنطقة والحالة والأرصدة، ولا يحتوي اسم مستخدم أو كلمة مرور.
   - جدولَا `beneficiary_auth_codes` و`beneficiary_sessions` يضافان عبر ترحيلات قاعدة البيانات، وليسَا حقولًا في جدول المستفيد.
   - لا توجد في المخطط الأساسي بيانات اعتماد باسم مستخدم وكلمة مرور للمستفيد. يجب تصميم تخزين بيانات الاعتماد قبل بناء شاشة الدخول.

6. **الرصيد**
   - الصيغة المرجعية في التطبيق الرئيسي هي `lib/domain/accounting/balance_sql.dart` عبر `BalanceSql.beneficiary`.
   - الصيغة تشمل الرصيد الافتتاحي والمرحّل والسقايات غير الملغاة وسلف الديزل اليدوية والدفعات المرحّلة وتسليم الديزل عندما يكون إعداد التسليم كرصيد مالي مفعّلًا.
   - الخادم لديه استعلام مستقل في `_beneficiaryAccount` داخل `server/lib/server.dart`. رغم تقارب الصيغة، فإن وجود نسختين مستقلتين خطر انحراف محاسبي؛ يجب اختبار تطابق الخادم مع صيغة التطبيق الرئيسي، بما فيها الحالات الحدية، قبل عرض الرصيد للمستفيد.

7. **الصلاحيات**
   - مسارات المستفيد الحالية محمية بمعالج `_beneficiaryAuth` وتربط الجلسة بمعرف مستفيد واحد.
   - يجب الحفاظ على عزل المستفيد: لا يقبل الخادم معرف مستفيد يرسله العميل لاختيار حساب آخر؛ يستخرج المعرف من الجلسة الموثقة، ويجب التحقق من المحطة أيضًا.

### قرارات التصميم المقترحة للدفعة التالية

- إضافة مدخل واضح «دخول المستفيد» إلى تجربة الدخول الحالية، مع بقاء دخول الإدارة كما هو. لا نضيف تطبيق Flutter جذريًا ثانيًا ولا `MaterialApp` ثانيًا.
- تحويل شاشة المستفيد إلى صفحات داخل التطبيق الرئيسي، مع إعادة استخدام خدمات API الموجودة بعد تحديث المصادقة.
- إنشاء بيانات اعتماد مستقلة للمستفيدين (يفضل جدولًا مخصصًا مرتبطًا بـ `beneficiary_id` و`station_id` واسم مستخدم فريد ضمن نطاق المحطة)، بدل تخزين كلمة المرور كنص أو خلطها بحقول الملف الشخصي.
- تخزين كلمة المرور باستخدام خوارزمية اشتقاق كلمات مرور بطيئة ومملحة ومعتمدة (مثل Argon2id أو bcrypt أو PBKDF2 بإعدادات قوية)، وليس SHA-256 منفردًا.
- إنشاء/تغيير بيانات دخول المستفيد من حساب إداري مخوّل، وعدم فتح التسجيل الذاتي لحسابات المستفيدين.
- إضافة تحديد محاولات الدخول، ورسائل خطأ لا تكشف هل اسم المستخدم موجود، وانتهاء الجلسة وإمكانية إلغائها، وعدم إرجاع أسرار المصادقة في API.
- جعل كل طلب API مقيدًا بالمستفيد الموثق والمحطة، واختبار منع الوصول إلى بيانات مستفيد آخر.
- اعتماد صيغة رصيد واحدة أو اختبار تكافؤ آلي بين SQL الخادم و`BalanceSql.beneficiary` قبل إطلاق الميزة.
